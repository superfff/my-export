本阶段需求摘要
异步导出任务的前后端已打通，前端在导出中心也能查到对应的 PENDING 状态导出任务信息。这个阶段完成 outbox模式的设计，引入 RabbitMQ ，进行任务投递进队列，消费者从队列取出的动作。完成前端请求申请 -> 后端outbox模式入库 -> 投递者取出消息投递至队列 -> 消费者竞争消息后执行的流程

    - 直接复用错误 `message` 展示
    - 检查前端判断逻辑


前端部分：
前端在本阶段实现后能查到 PENDING、RUNNING 的2种状态任务


后端部分：

1. 使用 docker 为项目加入 RabbitMQ 技术
    - java AMQP依赖等
    - 安装后检查 RabbitMQ 是否健康

2. 设计新的数据库
    - 创建 outbox_events 表（配合原有的export_jobs表完成outbox模式）
      1. 包括事件ID、关联的 jobId、创建时间、发布状态、投递者投递时间、导出尝试次数
      2. 当前端发起导出任务申请时，后端接受到请求后，在同一事务中同时为 export_jobs表写入信息，为outbox_events表写入信息

      （如果export_jobs已有数据、请同步迁移至 outbox_events表）
    - 创建 export_job_attempt 表，用于记录导出任务执行动作的信息
      1. 包括事件ID、关联的 jobId、创建时间、发布状态

3. RabbitMQ基础信息
    - 持久性的设计，当队列意外重启后，资源可恢复、broker接收的信息可持久性保留
    - 使用 directExchange 的交换机，配置正确的业务队列，和死信队列
    - 使用手动模式确认，确保每一个环节都收到确认后才可进行状态流转
    - 投递失败时，requeue 设为 true，重复投递超过5次仍然失败进入死信队列

4. 队列逻辑
    - 生产者 dispatcher 每5秒到 outbox_events 中扫描是否有 投递者投递时间（publish_at）为 null 的数据，取出数据放入队列中。收到 broker 的 confirm ack 和 broker 路由投递成功无return，才算成功，并更新 mySQL 里面的（publish_at）字段信息
    - 多个消费者在竞争时，使用乐观锁，抢占到并把 mySQL 的状态从 PENDING 改为 RUNNING 的才算成功，并将状态回写到2张表中。并在同一事务中，执行basicAck 将消息从队列中领走，并在 attempt 里面创建一条动作信息
    - 消息载体无需携带全量数据库，维护关键信息即可，保持消息的简单
    - 当 MQ 无法正常工作时，不因为不确定的动作而随意修改数据库状态，导致任务异常，数据保留在 mySQL，等待 MQ 恢复再进行工作


边界设定：
1. 允许重复投递，不允许重复执行
2. 同一事务的部分：
    - 不允许写入export_job表，但是没进入 outbox_event表，反之一样
    - 不允许先改了job状态，再进入MQ队列
3. 生产者 -> broker -> 消费者，每一个环节都需要有确认才可状态流转，结合 traceId 完成追踪
