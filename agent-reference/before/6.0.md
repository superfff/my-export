作为前端工程师，第一次创建全栈项目，目前前后端的框架已确定。


本阶段的需求摘要
完成导出接口的搭建，搭建导出任务的链路，本阶段先实现前端异步导出任务发起，后端接收任务后入库，完成导出job的持久化保存，为后续导出中心查询做准备
（本阶段不引入新技术）

前端部分：
1. 按照已维护好的业务场景和参数发送请求
    - "导出筛选结果"：根据筛选查询条件导出全量数据
    - "导出已选"：区分手动勾选模式、全选结合反选模式
2. 发送请求时请求头加入幂等值 `Idempotency-Key`，用于申请意图保护，让导出意图能被可靠保存。
    - 一次明确提交生成一个 Key，使用 crypto.uuid 生成
    - 网络失败、超时等情况幂等值复用
    - 成功提交提交请求、重新选择勾出信息时复用的幂等值失效
--- 

后端部分：
1. 完成基础搭建
    - 创建 export_jobs 表，用于保存异步导出任务的信息，按照描述创建对应字段
    - export_jobs 需记录两个"创建时快照"列（创建导出任务、校验通过入库前实时统计并写入），供导出中心展示与后续真正导出打底：
        1. 统计总条数：当前查询条件下命中订单的总条数
        2. 最大的 jobId：当前查询条件下命中订单的最大 t_order.id（jobId 指命中订单主键，作一致性水位）
    - 入库job维护清晰的状态机：
        1. PENDING:等待导出
        2. RUNNING:正在导出
        3. SUCCESS:成功
        4. FAILED:失败
2. 沿用 spring boot框架，遵循MVC分层搭建 export 导出申请的接口
    - 不沿用既有订单列表接口 GET /api/order，使用 restful 的形式独立搭建以 export-job 开头的导出请求
    - 接收前端多种交互场景：
        1. "导出筛选结果"：根据筛选查询条件导出全量数据
        2. "导出已选"：区分手动勾选模式、全选结合反选模式
    - 记录导出勾选列、文件名、交互场景的条件参数

3. 创建请求校验后写入 export_jobs，初始状态为 PENDING（写入时一并落上述"统计总条数 / 最大订单id"两个快照值）
4. 保存导出范围、导出列、文件名和筛选快照
    - 筛选快照根据：勾选导出列 + 导出范围条件做 hash 摘要 `request_hash`（jobId = 命中订单集合的最大 t_order.id，属上一步聚合结果，不作为 hash 输入；导出任务自增 id 建表前亦不可得）
5. 入库前校验前端请求头传入的幂等值 `Idempotency-Key`，用于判断请求的意图 
    - 判断数据库中是否有相同的幂等值
        1. 新的幂等值，等于新的导出任务可以入库
        2. 有重复的幂等值拒绝入库，结合判断快照 `request_hash` 返回错误码 409。有一样的快照提示：已有相同导出任务，不一样的快照提示：幂等值冲突


执行步骤（按顺序推进）：
1. 先创建数据库表，并完成迁移动作（遵循 flyway 逻辑）
2. 创建正确请求逻辑，打通前后端通道
3. 校验幂等值边界逻辑
