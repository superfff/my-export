# 阶段 8.0 完整实施提示语

> 来源：`agent-reference/before/8.0.md`
> 用途：可直接投喂给后续编码会话，指导其实现"异步导出任务可靠投递段 —— outbox 模式 + RabbitMQ（dispatcher 投递 → 消费者竞争领取置 RUNNING）"，以及前端幂等 409 展示缺陷修复。
> 性质：仅实施蓝图，本文档不含代码，也不对任何代码做过编辑。
> 约定沿革：上一阶段为 `7.0`（已打通"前端发起 → `export_jobs` 入库(PENDING) + 导出中心只读列表"，任务恒 PENDING、无任何推进路径）。阶段 `9.0` 之后才会引入真正执行导出 / 产出文件 / 推进 SUCCESS/FAILED 的能力；**8.0 的消费者"执行"只到"抢占并置 RUNNING"为止**。

## 一、背景与目标

全栈订单导出项目：`frontend/`（React18 + Vite + TS + AntD5 + pnpm）+ `backend/`（SpringBoot3 + Java21 + MyBatis-Plus + Flyway，端口 8080）+ MySQL（`order_db`）。信封统一 `ApiResponse{code,message,data,traceId}`，`code=0` 成功；`TraceIdFilter` 用 MDC 键 `traceId`、HTTP 头 `x-trace-id` 贯穿一次请求的日志。

**当前后端结构（可直接读到代码确认，均与 7.0 一致）**：

- 包：`com.example.{OrderApplication, common, config, order, export}`；`export` 自持 MVC：`controller/ExportJobController`、`service(+impl)/ExportJobService`、`mapper/ExportJobMapper`、`entity/ExportJob`、`dto/*`、`enums/*`。
- `POST /api/export-job`（创建）：`ExportJobServiceImpl.create` 现**只写 `export_jobs` 一行、无事务注解**；幂等重复时 `respondConflictByKey` 判 `request_hash`：相同 → `BizException(409,"已有相同导出任务")`，不同 → `BizException(409,"幂等值冲突")`。
- `export_jobs` 表字段（V2，唯一版本线到 V2，无其他迁移）：`id / idempotency_key / request_hash / export_mode / status / filename / export_columns / scope_snapshot / expected_total / max_order_id / created_at / updated_at`，`uk_idempotency_key` 唯一。
- `GET /api/export-job` 列表已支持 `status` 过滤（含 `RUNNING`），导出中心 tab（全部/待导出/导出中/成功/失败）与状态列渲染已在 7.0 就绪。
- `docker-compose.yml`：`mysql + backend + frontend` 三服务，无 RabbitMQ；`backend/pom.xml` 无 AMQP 依赖。
- `application.yml`：无 `spring.rabbitmq.*` 配置。
- 前端导出创建：`pages/order/index.tsx` 的 `handleExportConfirm` 持有幂等 Key 生命周期（`pendingRef`：内容签名不变则复用 Key），对 409 有两条分支：`message===EXPORT_409_MESSAGES.duplicate` → 提示"已创建导出任务"并关弹窗；`message===EXPORT_409_MESSAGES.conflict` → 提示自造文案"导出内容冲突，请重新确认后导出"并保留弹窗。常量 `constants/export.ts` 的 `EXPORT_409_MESSAGES` 两文案与后端**逐字一致**，仅作为判别串使用。

**本阶段目标**：

1. **修复前端幂等 409 展示缺陷**（第二节）：两条 409 都改为**直接复用后端返回的 `message` 原文展示**，不再使用前端自造文案；`duplicate`（该意图任务先前已创建）仍按成功闭环关弹窗，`conflict` 仍保留弹窗供重新确认。判断逻辑收敛为一个可测纯函数。
2. **引入 RabbitMQ 基础设施**（第三节）：docker 加 `rabbitmq` 服务；`spring-boot-starter-amqp` 依赖；broker 与队列持久性、direct 交换机 + 死信队列、手动 ack、消费侧有界重试满 5 次进死信；安装后验证 `/actuator/health` 显示 `rabbit: UP`。
3. **数据库设计（Flyway V3）**（第四节）：新增 `outbox_events`、`export_job_attempt` 两张表；把已有 `export_jobs` 中 `PENDING` 行 backfill 进 `outbox_events`（它们是"已入库但从未入队、仍需被消费"的行）。
4. **创建链路由"只写 job"改为"单事务写 job + outbox"**（第五节）：同一数据库事务内写 `export_jobs(PENDING)` 与 `outbox_events(status=PENDING)`，保证要么都在、要么都不在；outbox 行记录创建请求的 `traceId`，供整条投递链追踪。
5. **dispatcher（生产者）**（第六节）：每 5 秒扫描 `outbox_events` 中未投发行，投递到 RabbitMQ；收到 broker confirm 且无路由 return 后才回写 `published_at`/`status=PUBLISHED`。
6. **消费者（RabbitMQ 竞争消费）**（第七节）：从队列取消息，用乐观锁（状态即版本 CAS）把 `export_jobs` 由 `PENDING` 置 `RUNNING`；抢占成功者**在同一事务**记录一条 `export_job_attempt` 并回写 outbox `attempt_count`，随后 basicAck 从队列领走消息。
7. **端到端**：导出中心能查到 `PENDING、RUNNING` 两种状态任务（RUNNING 展示已在 7.0 具备，本期出现真实 RUNNING 行）。

**明确本期不做（防止实现越界）**：

- **不做真实导出**：消费者"执行"= 抢占成功置 `RUNNING` + 记一条 attempt；不读取 `scope_snapshot` 产出文件、不把任务推进 `SUCCESS/FAILED`。因此本期 `RUNNING` 任务会停留在 RUNNING（无推进路径），这是**合法中间态**，不是 bug（对齐 7.0 中 PENDING 恒不动的姿态；探活/恢复"卡死 RUNNING"的机制留到有真实执行能力的后续阶段）。
- **不新增 / 不改导出中心前端**：RUNNING 列、tab、Tag 渲染已具备；本期前端唯一改动是第二节的 409 缺陷修复。
- **不改 `export_jobs` 表结构、不改 `ExportJob` 实体 / `ExportJobVO` / 列表接口 / 两条 409 文案 / 幂等创建契约**：trace 存到 outbox 即可，不为此动 job 权威表。
- **不引入新依赖**（除 `spring-boot-starter-amqp`；其传递引入 spring-retry 供消费侧有界重试）、不引入消息中间件之外的存储 / MQ 管理 UI 之外的组件。
- **不做多实例分布式锁**：dispatcher 按"单后端实例"假设（docker-compose 现状即单实例）；即使误启多实例，最多重复投递，由消费者幂等领取兜底（见第八节拍板）。
- **不加外键约束**：与 V1/V2 建表风格一致（仅逻辑外键），避免迁移与数据回填时受约束掣肘。

## 二、修复 A：前端幂等 409 展示缺陷

### 现状（`pages/order/index.tsx` 的 `handleExportConfirm` 409 分支）

- `duplicate`（同幂等值 + 同 `request_hash`）：后端真实返回 `409` + message"已有相同导出任务"，前端却提示自造的"已创建导出任务"，**与后端语义不符**（后端并未新建）。
- `conflict`（同幂等值 + 异 `request_hash`）：后端 message"幂等值冲突"，前端却提示自造的"导出内容冲突，请重新确认后导出"，**文案与后端不一致**。

### 修复要求

1. **两条 409 的提示一律复用后端 `message` 原文**（`err.message`），前端不再拼接任何自定义文案。后端 message 即最终展示给用户的文本。
2. 判断逻辑与提示语义分开，逻辑收敛成可测纯函数，供单测锁定：
   - 在 `constants/export.ts` 新增判别函数（与 `EXPORT_409_MESSAGES` 同文件、共用同一常量表，避免文案与判别串漂移）：
     ```ts
     /** 409 两种语义判别：同 request_hash → duplicate；异 request_hash → conflict */
     export type Export409Kind = 'duplicate' | 'conflict';
     export function classifyExport409(message: string): Export409Kind {
       return message === EXPORT_409_MESSAGES.duplicate ? 'duplicate' : 'conflict';
     }
     ```
   - `handleExportConfirm` 的 409 分支改为按 `classifyExport409(err.message)` 分派，两条都展示 `err.message`：
     - `duplicate`：该幂等意图的任务先前已创建（如首次成功但响应丢失后的重试），后端没有新建——**展示后端原文后按成功闭环**（`clearPending()` + `setExportOpen(false)`，弹窗表单照常由 ExportModal 成功路径重置）；提示用中性风格（`message.info(err.message)`，避免再像"已创建"那样暗示新建）。
     - `conflict`：幂等值冲突，属异常生命周期——`message.error(err.message)` + `clearPending()`（作废当前 Key，下次确认换新 Key）+ 保留弹窗（不关闭、不清表单），与现行为一致。
   - 原有"网络失败/超时/5xx/400"兜底分支不变（保留 `pendingRef`，同内容重试复用同一 Key）。
3. `constants/export.ts` 中 `EXPORT_409_MESSAGES` 保留，其注释改为"与后端 `ExportJobServiceImpl` 逐字一致的判别串 + 展示文案"；`components/ExportModal/index.tsx` 中 `onConfirm` 的 javadoc（"Promise resolve 表示提交成功（含已有相同导出任务）"）语义仍成立，**无需改动**（duplicate 仍以 resolve 闭环）。
4. 新增最小单测：`constants/__tests__/export.test.ts`（新目录，若存在其它 constants 测试目录则并入），断言 `classifyExport409('已有相同导出任务')==='duplicate'`、`classifyExport409('幂等值冲突')==='conflict'`、其它字符串视为 `'conflict'`。

### 验收

- 复现：先用 curl 以幂等键 `K`、内容 X 创建成功；再用 `K`、内容 X 重发 → 后端返回 `409 已有相同导出任务`。前端手工注入该响应到创建请求（或按上述新增单测覆盖 `classifyExport409` 与分派）后确认：
  1. `duplicate`：toast 显示后端原文"已有相同导出任务"（不再显示"已创建导出任务"），弹窗关闭，`pendingRef` 清空；
  2. `conflict`：toast 显示后端原文"幂等值冲突"（不再显示自造文案），弹窗保留、表单不清空、`pendingRef` 清空；
  3. 网络失败 / 5xx / 400 等非 409 分支行为不变。
- 前端 `lint / typecheck / test / build` 全绿；`EXPORT_409_MESSAGES` 两串与后端仍逐字一致。

## 三、RabbitMQ 引入与基础信息

### docker-compose 增补 `rabbitmq` 服务

- 镜像 `rabbitmq:3.13-management`，容器名 `order-rabbitmq`，`restart: unless-stopped`。
- 环境：`RABBITMQ_DEFAULT_USER: order`、`RABBITMQ_DEFAULT_PASS: order123456`、`TZ: Asia/Shanghai`。
- 端口：`5672:5672`（AMQP）、`15672:15672`（management，登录 `order/order123456`）。
- healthcheck：`["CMD","rabbitmq-diagnostics","-q","ping"]`，`interval:5s timeout:5s retries:20`。
- 命名卷 `rabbitmq-data:/var/lib/rabbitmq`：**broker 意外重启后元数据与持久化消息可恢复**（配合下方"队列/消息持久性"）。
- `backend` 服务增补 `depends_on: rabbitmq: condition: service_healthy`，并注入环境 `RABBIT_HOST: rabbitmq`、`RABBIT_USER: order`、`RABBIT_PASSWORD: order123456`（端口用默认 5672）。

### 依赖与连接配置

- `backend/pom.xml` 新增 `spring-boot-starter-amqp`（含 `spring-rabbit`；其传递依赖 `spring-retry` 供容器重试）。
- `application.yml` 新增（沿用现有"环境变量注入 + 本地默认值"模式）：
  - `spring.rabbitmq.host=${RABBIT_HOST:localhost}`、`port=${RABBIT_PORT:5672}`、`username=${RABBIT_USER:guest}`、`password=${RABBIT_PASSWORD:guest}`；
  - `spring.rabbitmq.publisher-confirm-type: correlated`、`publisher-returns: true`（dispatcher 需要 confirm + 路由 return）；
  - `spring.rabbitmq.template.mandatory: true`；
  - `spring.rabbitmq.listener.simple.acknowledge-mode: manual`（手动 ack）；
  - `spring.rabbitmq.listener.simple.prefetch: 1`；
  - 消费侧有界重试**不进容器层**：manual ack 下容器不替消费者 reject，容器级重试耗尽后消息只悬在未确认态、到不了死信队列（已实测）。有界重试由消费者方法内 `RetryTemplate`（max-attempts=5、退避 `1s ×2`）承担，最终失败显式 `basicNack(requeue=false)` → 主队列 DLX。详见第七节。

### 交换机 / 队列拓扑（代码声明，不在管理台手点）

在一个 `com.example.config` 的 `RabbitConfig`（`@Configuration`）中用 `DirectExchange/Queue/Binding` Bean 声明，全部 durable：

```
export.exchange  (direct, durable)           业务交换机
   └── routing key: export.job → export.job.queue (durable,
        arguments: x-dead-letter-exchange=export.dlx,
                   x-dead-letter-routing-key=export.job.dlq)
export.dlx       (direct, durable)           死信交换机
   └── routing key: export.job.dlq → export.job.dlq (durable)
```

- 队列名 / 交换机名 / routing key 收敛为常量（如 `export/mq/RabbitNames`），业务代码只引常量，不散落字符串。
- 消息投递默认 persistent（Spring AMQP `MessageDeliveryMode.PERSISTENT`）——配合 durable 队列与数据卷，满足"队列意外重启后资源可恢复、broker 接收的信息可持久性保留"。
- `RabbitTemplate` Bean：`setMandatory(true)` + returns 兜底日志回调；发布确认与 returns 在连接工厂层开启（yml `publisher-confirm-type: correlated` / `publisher-returns: true`；Spring AMQP 3.x 的 `RabbitTemplate` 上没有 `setPublisherConfirmType` / `setPublisherReturns`，勿误加）。confirm 以 `CorrelationData`（id = outbox 行 id）关联，dispatcher 用 `cd.getFuture().get()` 读 `Confirm.isAck()`，`cd.getReturned() != null` 视为路由失败（拓扑静态，正常不应触发）。
- 手动确认：`acknowledge-mode: manual` 已全局设置，消费者代码显式 `basicAck`。

### 健康检查

`spring-boot-starter-amqp` 引入后 Actuator 自动暴露 `rabbit` 健康指标。验收：`GET /actuator/health` 中 `rabbit` 一节为 `UP`；docker healthcheck 亦验证 broker 本身可达。

## 四、数据库设计（Flyway V3）

新增 `V3__create_outbox_and_attempt.sql`（`backend/src/main/resources/db/migration/`），含三部分：建 `outbox_events`、建 `export_job_attempt`、backfill 已有 `PENDING` 任务。表用 utf8mb4 + InnoDB，不加物理外键（沿 V1/V2 风格，仅逻辑外键与索引）。

### outbox_events（outbox 事件表：记录"一条导出任务的投递生命周期"）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED AUTO_INCREMENT PK | 事件 ID |
| `job_id` | BIGINT UNSIGNED NOT NULL, UNIQUE `uk_outbox_job_id` | 关联 `export_jobs.id`（**1 任务 = 1 事件**） |
| `trace_id` | VARCHAR(64) NULL | 创建请求的 `traceId`（从 MDC 捕获）；历史 backfill 行为 NULL |
| `status` | VARCHAR(16) NOT NULL DEFAULT 'PENDING' | 发布状态 `PENDING/PUBLISHED` |
| `published_at` | DATETIME NULL | 投递成功（broker confirm 且无 return）时间 |
| `attempt_count` | INT NOT NULL DEFAULT 0 | 导出执行尝试次数（= 消费者成功领取次数，恒等于该任务 `export_job_attempt` 行数） |
| `created_at` | DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `updated_at` | DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 更新时间 |
| KEY `idx_outbox_pending(status, id)` | — | dispatcher 按 `status='PENDING'` 取最早一批 |

不变量：`status='PENDING' ⟺ published_at IS NULL`；二者只在 dispatcher 确认投递后由同一 UPDATE 一起翻转（`status='PUBLISHED', published_at=NOW()`）。扫描一律用 `status='PENDING'`。

### export_job_attempt（导出任务执行尝试表：记录"消费者每次领取执行的动作"）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED AUTO_INCREMENT PK | 尝试记录 ID |
| `event_id` | BIGINT UNSIGNED NOT NULL | 关联 `outbox_events.id`（消费者按消息 `eventId` 落账，与消息体对齐） |
| `job_id` | BIGINT UNSIGNED NOT NULL | 关联 `export_jobs.id` |
| `attempt_no` | INT NOT NULL | 该任务第几次执行（配合 CAS 单次领取，本期恒 1） |
| `status` | VARCHAR(16) NOT NULL | 执行状态 `RUNNING/SUCCESS/FAILED`（本期恒 `RUNNING`） |
| `started_at` | DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP | 开始执行时间 |
| `finished_at` | DATETIME NULL | 结束时间（后续真实导出阶段回填） |
| `error_message` | VARCHAR(1000) NULL | 失败原因（后续阶段回填） |
| `created_at` | DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| UNIQUE `uk_job_attempt(job_id, attempt_no)` | — | 同任务同序号不重复（CAS 幂等领取的兜底） |
| KEY `idx_attempt_event(event_id)` | — | 按消息事件查尝试记录 |

### backfill 历史数据

同一 V3 内，将 `export_jobs` 中仍可被消费的 `PENDING` 行同步为 outbox 事件（它们从未入队）：

```sql
INSERT INTO outbox_events (job_id, trace_id, status, published_at, attempt_count)
SELECT id, NULL, 'PENDING', NULL, 0
FROM export_jobs
WHERE status = 'PENDING';
```

- 仅 `PENDING` 行需要入队；`RUNNING/SUCCESS/FAILED` 行不 backfill（`RUNNING` 由本阶段新代码产生、必已带 outbox 行；`SUCCESS/FAILED` 后续阶段才会出现）。
- 期望结果：部署本阶段后，库里历史 `PENDING` 任务会被 dispatcher 陆续投递、被消费者置为 `RUNNING`——导出中心里这批任务从"待导出"变为"导出中"，是**预期行为**（8.0 尚无真实导出，它们将停留在 RUNNING）。

## 五、后端改动 A：创建链路改为"单事务写 job + outbox"（在 export 模块内）

新增实体与 Mapper：`export/entity/OutboxEvent.java`、`export/entity/ExportJobAttempt.java`（`@TableName` 对应两表，字段驼峰映射同现状）；`export/mapper/OutboxEventMapper.java`、`export/mapper/ExportJobAttemptMapper.java`（`@Mapper`，同现有风格）。

`ExportJobServiceImpl.create` 改造（接口签名与返回 VO 不变、校验顺序不变、409 判别不变）：

1. 方法级 `@Transactional`（导入 `org.springframework.transaction.annotation.Transactional`），使"job 入库 + outbox 入库"成为同一个数据库事务。
2. 第 4 步组装 `ExportJob` 时，从 MDC 捕获创建请求 traceId（键 `traceId`，可能为空则留 null）。
3. `exportJobMapper.insert(job)` 成功（拿到 `job.getId()`）后，**同一事务**内插入 `OutboxEvent`：`job_id=job.getId()`、`trace_id=捕获值`、`status=PENDING`、`attempt_count=0`。
4. 插入 outbox 失败则整体回滚（job 也不落库）；job 唯一键冲突走原 `respondConflictByKey`（该分支抛 409 时事务回滚、不写 outbox）。**不变量：job 与 outbox 同生同灭。**
5. 事务提交后返回 `ExportJobVO`（读回逻辑不变）。

此处"先改 job 状态再进队列"被明确禁止的边界由**消费者侧时序**保证：状态 `PENDING→RUNNING` 只发生在消费者从队列领到消息之后，任何代码都不得在投递前推进 job 状态（见第七节；八节第 2 条一并覆盖）。

## 六、后端改动 B：dispatcher（生产者，每 5 秒扫描 outbox → 投递 → 确认后回写）

新建 `export/outbox/OutboxDispatcher`（`@Component`，`@EnableScheduling` 可在 `OrderApplication` 或某配置类开启）：

1. `@Scheduled(fixedDelay = 5000, initialDelay = 2000)`（约每 5 秒一轮，`fixedDelay` 避免轮次重叠；`initialDelay` 让位给 Rabbit 连接建立）。方法体内并发安全无需处理（单实例；多实例最坏重复投递，见八节拍板）。
2. 每轮：
   1. 查 `outbox_events` 中 `status='PENDING'` 的行，`ORDER BY id ASC LIMIT 100`；
   2. 为空则结束本轮；不为空，逐条构造**轻量消息**（见下）并投递。
3. **消息载体保持简单**，只维护关键信息、不携带全量数据库：
   ```json
   { "version": 1, "eventId": 12, "jobId": 34 }
   ```
   消费者如需 job 全量信息（`scope_snapshot` 等）一律按 `jobId` 回查 `export_jobs`。消息**头**携带 `x-trace-id` = 该 outbox 行的 `trace_id`（为空则投递时生成一个 UUID 兜底），并写入本轮 MDC 供投递日志追踪。
4. **发布与确认**（用 `RabbitTemplate.invoke(ops -> …)` 批量发送 + 等待 confirm）：每条 `convertAndSend(EXCHANGE, RK_EXPORT_JOB, message, new CorrelationData(String.valueOf(eventId)))`，把 CorrelationData 收集起来；invoke 返回后逐条判断：
   - `cd.isAck()==true` 且**无路由 return** → 判定投递成功，执行 `UPDATE outbox_events SET status='PUBLISHED', published_at=NOW() WHERE id=:eventId AND status='PENDING'`（加 `status='PENDING'` 条件防重复回写）；
   - 否则视为失败：**不改任何数据库状态**，该行保持 `PENDING`，下轮再投。日志记录失败原因（含 traceId、eventId）。
   - 失败计次不是必需（MQ 恢复后自然补投），但**不得**在失败时把 job/outbox 置 FAILED 或丢数据。
5. **MQ 不可用时的降级**：`convertAndSend` 抛连接类异常时捕获并记日志、结束本轮——`export_jobs`/`outbox_events` 的数据库状态保持原样（任务停在 PENDING、未发布行停 PENDING），等待 MQ 恢复后由后续轮次补投。**不因不确定的动作随意改库。**

**验收（单元无、以运行验证为主）**：

- 创建任务后 ≤6 秒，outbox 行变 `PUBLISHED` 且 `published_at` 非空；日志里 dispatcher 与后续消费者共享同一 `traceId`。
- 停掉 rabbit 容器后创建任务：`export_jobs` + `outbox_events` 都落库成功（PENDING/PENDING），不报错；重启 rabbit 后 ≤10 秒该任务被补投。

## 七、后端改动 C：消费者（从队列取消息 → 乐观锁抢占置 RUNNING → 记 attempt → ack）

新建 `export/outbox/ExportJobConsumer`（`@Component` + `@RabbitListener`），及供其调用的业务方法（放 `ExportJobService` 接口 + `ExportJobServiceImpl`，保持 MVC 分层、可单测）。

### 消费主流程

`@RabbitListener(queues = RabbitNames.QUEUE_EXPORT_JOB)`（手动 ack 已全局配置）：

1. 解析消息为 `ExportEventMessage{version,eventId,jobId}`（与投递体同构的 record，放 `export/mq/ExportEventMessage`）；解析失败抛异常（进入方法内有界重试，见下）。
2. 把消息头 `x-trace-id` 写入 MDC（键 `traceId`），处理结束 `finally` 清除——消费者日志与 dispatcher/创建请求日志同链。
3. 调业务方法 `boolean claimAndRun(eventId, jobId)`（`@Transactional`）：
   1. **乐观锁抢占（状态即版本，无独立 version 列）**：`UPDATE export_jobs SET status='RUNNING', updated_at=NOW() WHERE id=:jobId AND status='PENDING'`；
      - 影响行数 = 1 → 抢占成功；
      - 影响行数 = 0 → 抢占失败（已被其它消费者领取 / 已非 PENDING，如重复投递或历史终态），**返回 false，不写任何东西**。
   2. 抢占成功后**同一事务**内**同时落定两处状态**（任务级 + 本次执行级，任一处失败整体回滚，不会出现"任务已 RUNNING 但无执行记录"）：
      - 任务级（`export_jobs`）：上面的 CAS 已把 `status` 由 `PENDING→RUNNING`——即"任务导出表"的任务状态；
      - 本次执行级（`export_job_attempt`）：把该事件 `attempt_count` 加 1（`UPDATE outbox_events SET attempt_count=attempt_count+1 WHERE id=:eventId`），`attempt_no = 加 1 后的值`，插入一条 `status='RUNNING'`、`started_at=NOW()` 的执行记录——即"导出动作表"记载本次执行的状态。
   3. 返回 true。
4. 依据返回值处理 ack：方法正常返回（true/false 皆可）→ `channel.basicAck(deliveryTag, false)` 领走消息；业务执行抛异常 → **不 ack**，由方法内 `RetryTemplate`（max-attempts=5、退避 `1s ×2`）自动有界重试（消息保持未 ack）；重试耗尽仍失败 → 见下"失败与死信"。
5. **ack 与 DB 事务的一致性说明**：`claimAndRun` 作为独立 `@Transactional` Bean 方法，其返回即代表 DB 提交成功，随后才 ack——即"DB 抢占成功后才从队列领走消息"。若进程在 DB 提交后、ack 前崩溃，消息会**重复投递**；届时 `claimAndRun` 抢占必为 0 行（job 已 RUNNING），消费者直接 ack 丢弃——达成"**允许重复投递，不允许重复执行**"（靠 CAS + attempt 唯一索引兜底，而非消息级去重）。

### 失败与死信（消费侧重试 5 次进死信）

- 监听器在 manual ack 下对消息 outcome 全权负责：解析失败 / DB 异常等在重试耗尽前**不 ack**，由方法内 `RetryTemplate(maxAttempts=5, 指数退避 1s ×2)` 自动重试（与容器级重试同为 spring-retry、同语义）；耗尽仍失败 → 消费者显式 `channel.basicNack(deliveryTag, false, false)`（requeue=false）→ 因主队列声明了 DLX，消息进入 `export.job.dlq` 死信队列。
- **为何不用容器级重试（`retry.enabled + max-attempts=5 + default-requeue-rejected=false`）**：manual ack 下容器不替消费者执行终端 reject——容器级重试耗尽后 `ConditionalRejectingErrorHandler` 仅记日志，消息永远悬在未确认态（unacked 不释放、不进死信），已实测确认。故把重试与终端处置收敛到消费者方法内，保持"重试满 5 次进死信"的观察语义不变。
- **对原文"投递失败时 requeue 设为 true，重复投递超过 5 次仍然失败进入死信队列"的等价解读**：重试期间消息保持未 ack、可被重新执行（进程崩溃则重连后重投），等价于 requeue；第 5 次后仍失败才 basicNack 放行到死信。原始以 `basicNack(requeue=true)` 逐次重投到 broker 的做法在 Rabbit 无内置投递计数、需额外延迟队列与 x-death 计数，复杂度高且本期消费者几乎不会真实失败（执行仅是抢占+落账），故收敛为消费侧有界重试（八节拍板确认的语义等价实现）。
- **本期真实失败面极小**：`claimAndRun` 抢占失败走"返回 false → ack"（不是异常，不进重试）；只有解析失败、DB 异常等才会触发重试。死信链路作为基础设施本期就位并按下述方法验证，无需构造业务失败。

### 验收（含死信与重复投递验证）

- **端到端**：curl/UI 创建任务 → ≤6 秒 `export_jobs` 置 `RUNNING`、`export_job_attempt` 恰 1 行 `RUNNING`、outbox 变 `PUBLISHED` 且 `attempt_count=1`；导出中心"导出中"tab 能查到该任务。
- **重复投递不重复执行**：向 `export.job.queue` 手动再投同一条消息（`docker exec order-rabbitmq rabbitmqadmin -u order -p order123456 publish exchange=export.exchange routing_key=export.job payload='{"version":1,"eventId":<该任务eventId>,"jobId":<该任务jobId>}'`）→ 任务保持 `RUNNING`、`export_job_attempt` 仍 1 行（不新增）。
- **死信链路**：向 `export.job.queue` 投一条**非法 payload**（如坏 JSON）→ 监听器解析失败、方法内重试 5 次后消息出现在 `export.job.dlq`（`docker exec order-rabbitmq rabbitmqctl list_queues name messages` 观察 `export.job.dlq` 消息数=1）；DB 无任何 RUNNING/attempt 副作用。
- **trace 贯穿**：同一任务从创建请求日志 → dispatcher → 消费者日志使用同一个 `traceId`。
- **重启恢复**：`docker restart order-rabbitmq` 后队列/交换机声明仍在（应用声明式）、已持久化消息可继续消费。

## 十、已拍板的解读（可在实施前推翻）

1. **消费者"执行"边界 = 仅抢占置 RUNNING + 记一次 attempt**：真实文件导出 / SUCCESS/FAILED 推进留到后续阶段；本期 `RUNNING` 任务停留在 RUNNING 是合法中间态。前端本期只需看到 PENDING/RUNNING（7.0 已具备展示，无新增 UI）。
2. **"同一事务的部分"边界的落地**：写 job 与写 outbox 在同一 DB 事务（同生同灭）；"先改 job 状态再进队列"被禁止的落地 = job 状态只在消费者**领取后**推进，dispatcher/创建链路永不改 job 状态。
3. **"回写到 2 张表"解读：两张表都更新状态，但语义分层、互不覆盖**：
   - `export_jobs.status`（任务级状态机）：PENDING→RUNNING，后续真实导出阶段由任务最终结果驱动到 SUCCESS/FAILED，代表"任务当前所处阶段"；
   - `export_job_attempt.status`（本次执行级状态）：一次执行开始即 RUNNING，后续真实导出阶段在该次执行结束回填 SUCCESS/FAILED（连同 `finished_at`/`error_message`）；
   - 消费者抢占成功时在**同一事务**同时落定这两处（`export_jobs` 置 RUNNING + 插入一条 `status=RUNNING` 的 attempt），任务级 = 该次执行状态的投影；本期 1 任务 = 1 次执行，两表恒同步。`outbox_events` 只承载发布生命周期（status/published_at/attempt_count），不重复存任务状态。
4. **`export_job_attempt` 字段语义修正**（原摘要字段疑似复制错位、含与执行无关的"发布状态"）：改为 `event_id/job_id/attempt_no/status/started_at/finished_at/error_message`；本期恒 `status=RUNNING`、`attempt_no=1`、后两列留空。
5. **乐观锁 = 状态即版本 CAS**（`WHERE status='PENDING'` 影响行数判别），不引入独立 version 列；重复投递由"抢占 0 行 → ack 丢弃"天然幂等。
6. **"requeue=true、5 次进死信"采用消费侧有界重试**（manual ack 下容器级重试耗尽后不落地 reject、消息悬死无法进死信——已实测，故不用 `retry.enabled + default-requeue-rejected`）；等价实现为：消费者方法内 `RetryTemplate(maxAttempts=5, 指数退避)` 重试 + 最终失败显式 `basicNack(requeue=false)` → DLX；不引入延迟/重试队列 + x-death 计数的重模型。
7. **`attempt_count` 的语义** = 消费者成功领取执行次数，恒等于该任务 `export_job_attempt` 行数；"发布状态"列保留但仅 `PENDING/PUBLISHED` 两态，与 `published_at` 同翻。
8. **traceId 链路**存于 `outbox_events.trace_id`（创建请求 MDC 捕获），经消息头 `x-trace-id` 贯通 dispatcher→消费者；不为此改 `export_jobs`。历史 backfill 行 trace 为空时，dispatcher 投递时生成 UUID 兜底。
9. **单实例假设**：dispatcher 按单后端实例设计（docker-compose 现状）；多实例最坏重复投递，由消费者 CAS 兜底，不引入分布式锁。
10. **不加外键**（逻辑外键 + 唯一索引即可），沿用 V1/V2 风格；历史 PENDING 行会被本阶段投递并置为 RUNNING，属预期。
11. **前端 409**：提示一律用后端 `message` 原文；`duplicate` 仍以"关弹窗"闭环（任务确实已存在、意图已满足），但用中性文案，不再误导为"新建成功"；判别逻辑收敛为可测纯函数 `classifyExport409`。
12. **（前瞻，本期不实现，仅对齐将来口径）**：当任务将来允许"失败后重试成新一次执行"时，一个任务会有多条 attempt，规则为——`export_job_attempt` 每行记一次执行及该次结果；`export_jobs.status` 取**最近一次执行的结果**作为任务级状态。本期 1 任务 = 1 次执行，两表恒一致，故只在该表/实体注释处体现即可，不影响本期实现。
