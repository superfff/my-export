## 一、背景与目标

全栈订单导出项目：`frontend/`（React18 + Vite + TS + AntD5 + pnpm）+ `backend/`（SpringBoot3 + Java21 + MyBatis-Plus + Flyway + RabbitMQ，端口 8080）+ MySQL（`order_db`）+ RabbitMQ。信封统一 `ApiResponse{code,message,data,traceId}`；`TraceIdFilter` 以 MDC 键 `traceId`、HTTP 头 `x-trace-id` 贯穿一次请求日志。

**当前后端结构（可直接读到代码确认，均为 8.0 落地产物）**：

- `export` 模块自持 MVC：`controller/ExportJobController`、`service(+impl)/ExportJobService`、`mapper/*`、`entity/ExportJob、OutboxEvent、ExportJobAttempt`、`dto/ExportCreateRequest、ExportJobQueryDTO、ExportJobVO`、`enums/ExportJobStatus、ExportMode`、`outbox/OutboxDispatcher`、`mq/RabbitNames、RabbitTopologyConfig、ExportEventMessage、ExportJobConsumer`、`config/RabbitConfig`。
- 表结构（唯一版本线到 V3）：
  - `export_jobs`（V2）：`id / idempotency_key(uk) / request_hash / export_mode / status(PENDING/RUNNING/SUCCESS/FAILED) / filename / export_columns(JSON 数组, 保序) / scope_snapshot(JSON: mode+query+ids) / expected_total / max_order_id / created_at / updated_at`。`max_order_id` 语义 = 创建时命中订单最大 `t_order.id`（一致性水位）；`expected_total` = 创建时命中订单总数（进度分母）。
  - `outbox_events`（V3）：`id / job_id(uk,1任务=1事件) / trace_id / status(PENDING/PUBLISHED) / published_at / attempt_count / created_at / updated_at`，`idx_outbox_pending(status,id)`。**status 列本阶段移除**（见第四节）。
  - `export_job_attempt`（V3）：`id / event_id / job_id / attempt_no(uk job_id+attempt_no) / status(RUNNING/SUCCESS/FAILED) / started_at / finished_at / error_message / created_at`。
  - `t_order`（V1，只读）：`id / order_no / customer_name / phone / status(TINYINT 1/2/3) / amount DECIMAL(12,2) / created_at / updated_at / remark`。
- 行为现状：
  - `POST /api/export-job`（`ExportJobServiceImpl.create`，`@Transactional`）：校验 → `request_hash` → 只读聚合 `selectExportScopeStats`（按 scope 取 count + max(id)，`OrderMapper` 单条 SQL）→ 同一事务 insert `export_jobs(PENDING)` + `outbox_events(PENDING, trace_id=MDC)`；幂等 409 判别 `request_hash`。
  - `OutboxDispatcher`（`@Scheduled(fixedDelay=5000)`）：扫 `outbox_events.status='PENDING'`，投递轻量消息 `{"version":1,"eventId","jobId"}`（头带 `x-trace-id`），`RabbitTemplate.invoke` + `CorrelationData` 判定 **confirm 且无 return** 才 `UPDATE status=PUBLISHED, published_at=NOW() WHERE id=? AND status=PENDING`；失败不改库、下轮补投。
  - `ExportJobConsumer`（`@RabbitListener(export.job.queue)`，manual ack，prefetch=1）：`retryTemplate(maxAttempts=5, 1s×2 退避)` 内 `claimAndRun(eventId, jobId)`（`@Transactional`：CAS `PENDING→RUNNING`，抢到则同一事务 `outbox.attempt_count+1` + insert `export_job_attempt(RUNNING)`），返回后立即 `basicAck`；抢不到（0 行）也 ack 丢弃；重试耗尽 `basicNack(requeue=false)` → DLX。
  - `application.yml`：`spring.rabbitmq.*`（correlated confirm / publisher-returns / manual ack / prefetch=1），**无 concurrency**（消费者默认 1）；无 `export.*` 自定义配置。
  - `docker-compose.yml`：`mysql + rabbitmq + backend + frontend`；backend 已注入 RABBIT_*，无 `EXPORT_FILE_DIR`、无导出文件卷。
  - `backend/pom.xml`：**无 POI 依赖**。
  - `backend/src/test/`：**为空**（后端无单测；前端有 vitest）。

**当前前端结构（可直接读到代码确认）**：

- `pages/order/index.tsx`：`PageTable` 双模式行选择；`handleExportConfirm` 已把 手动勾选（`mode=SELECTED`，`selectedIds`）与 全选反选（`mode=ALL_EXCLUDE`，`excludedIds` + `filterQuery(query)`）两个"导出已选"分支拼成 `ExportJobRequest`，两条 id 数组**均已 `.sort((a,b)=>a-b)` 升序**后进 body；`buildSignature` 亦对 id 排序做幂等签名。
- `pages/export-center/index.tsx`：只读列表，列含 导出实际条数(`actualTotal`)、状态、进度(`progress`)、完成时间(`finishedAt`)、文件大小(`fileSize`)；`resolveExportProgress(job)` 优先读 `job.progress`，否则 `actualTotal/expectedTotal`，缺省显示 `'-'`。**当前后端不返回 actualTotal/progress/finishedAt/fileSize，均为预留占位 → 本期进度由新字段 `processedRows` 驱动，见第十节。**
- `constants/export.ts`：`EXPORT_409_MESSAGES` / `classifyExport409` / `EXPORT_MODE_TEXT` / `EXPORT_JOB_STATUS` / `EXPORT_JOB_STATUS_TABS`；`constants/__tests__/export.test.ts` 存在（覆盖 classifyExport409）。
- `types/order.ts`：`ExportJobVO`（六字段）、`ExportCenterJob extends ExportJobVO`（含 4 个预留可选字段）、`SelectionMode`、`ExportMode` 等。

**本阶段目标**：

1. **前端请求参数优化（锁定，第二节 + 第三节）**：两个"导出已选"场景（手动勾选 / 全选反选）的 id 数组请求参数升序传给后台——现状已升序，收敛为共享纯函数并加单测锁定；若读码发现任何分支未升序则修复。
2. **后端数据模型精简（第四节 + 第五节）**：移除 `outbox_events.status` 列（与 `published_at` 重复、无实际逻辑），同步迁移、实体、dispatcher、常量；`export_jobs` 增 `processed_rows`（进度）。
3. **消费者从"领到即止"变为"真实执行"（第六～八节）**：抢占置 RUNNING 后，按冻结范围批量读 t_order（快照 + 高水位 + keyset 游标）→ SXSSF 流式写 excel（分批推进 processed_rows）→ 终态 SUCCESS/FAILED 落两处（job + attempt）→ 之后才 basicAck。prefetch=1 + concurrency=2 并行 2 消费者，**同一时刻一个消费者只领取一条并执行完再 ack**，结构性杜绝"先把多条置 RUNNING 再执行"。
4. **进度展示（第十节）**：前端以 `processed_rows / expected_total` 渲染进度条，**最大 99%**（SUCCESS 才到 100）。
5. **验证 8.0 关键节点未回退（第十二节验收）**：幂等 409、outbox 同生同灭、dispatcher confirm 后才 PUBLISHED、多消费者只一个抢到、重复投递不重复执行。

**明确本期不做（防止越界）**：

- **不提供下载 / 不做"最终文件"的对外提供**：excel 生成后保留在本地导出目录（`export.file-dir`），不建下载接口、不做文件归档/删改策略；job 生成完成即置 SUCCESS（裁决见第二节 R2）。
- **不做"卡死 RUNNING"的探活/恢复**：消费者在"置 RUNNING 已提交、终态未落"窗口崩溃会留下 RUNNING（重复投递会被幂等丢弃），本期不自动恢复，只留日志与文档说明（对齐 8.0 姿态，恢复机制留后续阶段）。
- **不引入分布式锁 / 不加物理外键 / 不加消息级去重**：沿用"允许重复投递，不允许重复执行"（job CAS + attempt 唯一索引兜底）。
- **不改幂等创建契约 / 409 文案 / 不改 export_columns、scope_snapshot、max_order_id、expected_total 语义**：这些都是现成冻结字段，导出执行直接消费它们。
- **不新增导出模式、不改导出中心既有列与 tab、不做前端下载按钮**。
- **不改 8.0 的表职责分层**：`export_jobs.status`=任务权威状态、`export_job_attempt.status`=本次执行状态、`outbox_events` 只承载发布生命周期（本期减负为 published_at 即"是否已发布"）。

## 三、前端改动 A：两个"导出已选"场景的 id 升序（锁定 + 单测）

现状 `pages/order/index.tsx` 的 `handleExportConfirm` 已对两条路径排序：
- 手动勾选 → `body.mode=SELECTED`，`selectedIds = Array.from(selectionState.selectedIds).sort((a,b)=>a-b)`；
- 全选反选 → `body.mode=ALL_EXCLUDE`，`excludedIds = Array.from(selectionState.excludedIds).sort((a,b)=>a-b)` + `query=filterQuery(query)`。

要求（**若读码后发现任一分支未升序，先修复；否则为纯锁定改动**）：

1. 在 `constants/export.ts` 增加共享纯函数，两分支统一调用（消除内联重复）：
   ```ts
   /** id 数组升序（副本，不改原 Set），供两个"导出已选"场景的请求参数统一排序 */
   export function ascSortedIds(ids: Iterable<number>): number[] {
     return [...ids].sort((a, b) => a - b);
   }
   ```
   替换 `handleExportConfirm` 中两处 `Array.from(...).sort(...)`。
2. 新增/扩充单测（`constants/__tests__/export.test.ts`）：
   - `ascSortedIds`：乱序输入→升序；已升序→幂等；含重复→保留去重前的值并按升序；空集→`[]`。
   - （建议）对导出请求体做一次快照式断言：手动勾选分支 `body.selectedIds` 升序、全选分支 `body.excludedIds` 升序（可直接测 `handleExportConfirm` 之前提取出的"body 组装"纯函数，或维持现状由人工/既有 UI 测试兜底；不要为此引入重型组件测试）。
3. 不改后端排序契约：后端 `ExportJobServiceImpl.dedupeSorted` 已再兜底升序去重，前端排序是契约一致性与幂等签名稳定所需。
4. 回归：`lint / typecheck / test / build` 全绿。

> 说明：该需求本质是"优化请求参数规范"。现状已达标，因此本改动收敛为"共享函数 + 单测锁定"，防止后续回归时漏排序。不要改 `buildSignature` 的排序（它本就独立排序）。

## 四、数据库迁移（Flyway V4 + V5）

新增两个迁移文件（`backend/src/main/resources/db/migration/`）：

### V4__drop_outbox_status.sql

```sql
-- V4: outbox_events 移除 status 列。发布与否以 published_at IS NULL 为准（status 与 published_at 冗余且无实际逻辑）。
-- 先删以其为首列的联合索引（MySQL 单条 ALTER 内先 DROP INDEX 再 DROP COLUMN），避免残留退化索引。
ALTER TABLE outbox_events
    DROP INDEX idx_outbox_pending,
    DROP COLUMN status;
```

要点：
- 移除后不再有 `idx_outbox_pending`。dispatcher 扫描是 `published_at IS NULL ORDER BY id LIMIT n`，走主键 id 序即可，**无需补建新索引**（`published_at IS NULL` 不是高效范围，别为它造复合索引）。
- 存量库：`status` 列与数据一并删除，历史行的发布状态只由 `published_at` 表达（8.0 已保证 `PENDING ⟺ published_at IS NULL`，故删列不丢信息）。全新库：Flyway 按 V1→V4 顺序执行，V3 建列、V4 删列，属正常。

### V5__add_export_jobs_processed_rows.sql

```sql
-- V5: export_jobs 增加导出进度字段（已成功写入文件的行数）。
ALTER TABLE export_jobs
    ADD COLUMN processed_rows BIGINT UNSIGNED NOT NULL DEFAULT 0
        COMMENT '已处理行数:已成功写入excel的行数,导出进度;RUNNING期间分批递增,终态=实际导出数'
        AFTER max_order_id;
```

`processed_rows` 不重建索引；`updated_at` 由 DDL `ON UPDATE CURRENT_TIMESTAMP` 自动刷新，无需手动 set。

## 五、后端改动 A：outbox status 移除的代码侧连锁

所有涉及 `outbox_events.status` 的代码按以下清点处理（改完 grep `getStatus/setStatus` 于 `OutboxEvent`/`ExportJobService*`/`OutboxDispatcher` 确认无残留）：

1. **实体** `export/entity/OutboxEvent.java`：删 `status` 字段与 getter/setter；类注释改为"outbox_events 记录一条任务的投递生命周期；发布与否以 `published_at IS NULL` 判定（dispatcher 扫描依据），不再有 status 列"。`created_at/updated_at/published_at/attempt_count` 保留。
2. **创建链路** `ExportJobServiceImpl.create`：删 `event.setStatus(OUTBOX_PENDING)`；删类常量 `OUTBOX_PENDING/OUTBOX_PUBLISHED`（文件内无其它引用则一并删）；方法注释"job + outbox 同生同灭（outbox 初始为未发布：published_at 空）"。
3. **claim** `ExportJobServiceImpl.claim`（现 `claimAndRun`）：仅 `outbox.attempt_count+1`，未引用 status，无需改；注释更新为不再提 outbox.status。
4. **dispatcher** `OutboxDispatcher`：
   - 常量 `OUTBOX_PENDING/OUTBOX_PUBLISHED` 删除；
   - 扫描谓词：`.eq(OutboxEvent::getStatus, PENDING)` → `.isNull(OutboxEvent::getPublishedAt)`，`orderByAsc(id)` + `LIMIT BATCH_SIZE` 不变；
   - `markPublished`：`.eq(status,PENDING)` 防重复回写 → `.isNull(OutboxEvent::getPublishedAt)`（同一条 UPDATE 设 `published_at=NOW()`）；
   - 类注释与"可靠性要点"同步改为"未发布 ⟺ published_at IS NULL"。
5. **文档同步**：`agent-reference/after/2026-09-04-phase8-db-state-flow.md` 内所有 status/published 不变量表述在本阶段作废——按仓库惯例在本阶段收尾时新写/更新一份 phase9 的 DB 状态流 after-doc（记录 V4/V5、outbox 新判据、job/attempt 终态回写路径），避免给 phase10 留下过时参考。

## 六、后端改动 B：消费者执行器重构（claim / execute / finalize / ack 时序）

这是本阶段最关键的时序改动：**8.0 是"领取后立即 ack"，9.0 是"领取后真执行、落定终态、才 ack"**。

### 接口与实现拆分（`ExportJobService` + `ExportJobServiceImpl`）

把现有 `claimAndRun` 改名/收敛为两条方法，消费者与接口注释一并更新：

```java
/**
 * 抢占并开始本次执行：CAS 把 export_jobs 由 PENDING→RUNNING；抢到则同一事务
 * outbox.attempt_count+1 并 insert 一条 status=RUNNING 的 export_job_attempt。
 * @return true=本消费者抢占成功；false=未抢到(重复投递/已非 PENDING)，调用方应 ack 丢弃
 */
boolean claim(long eventId, long jobId);

/**
 * 真实执行（仅 claim 返回 true 后调用，方法内不再做抢占）。
 * 按 export_jobs 冻结的 scope_snapshot/max_order_id keyset 分批发读 t_order，
 * SXSSF 流式写 excel，每批成功后推进 export_jobs.processed_rows。
 * 方法内部自行保证终态：全部成功→job/attempt=SUCCESS；任一步失败→尝试 job/attempt=FAILED 并落 error_message。
 * 仅当"终态本身也无法落库"（如 DB 完全不可用）才抛出，交由调用方死信/重投兜底。
 */
void executeExport(long jobId);
```

`claim` = 现 `claimAndRun` 的函数体原样保留（CAS + attempt_count + insert attempt），只改签名与注释。

### 消费者主流程（`ExportJobConsumer.onMessage`）

新时序（manual ack，prefetch=1，concurrency=2）：

```text
取到消息
  └─ 写 x-trace-id 进 MDC
  └─ [有界重试 5 次] 反序列化 ExportEventMessage → claim(eventId, jobId)   // 只重试"短事务"段
       ├─ claim=false（未抢到/已终态/重复投递）→ basicAck 丢弃，结束
       └─ claim=true → executeExport(jobId)
             ├─ 成功：job+attempt=SUCCESS（终态已提交）→ basicAck
             └─ 业务/查询/写批失败：executeExport 内部已 finalize FAILED → basicAck
       └─ 重试耗尽仍抛（解析失败 / claim 一直 DB 异常）→ basicNack(requeue=false) → DLX → export.job.dlq
  └─ 清 MDC
```

实现要点：
- **只把"解析 + claim"放进 `RetryTemplate`**（短、幂等、可重入安全）；`executeExport` 放在重试之外单次调用——因为 execute 一旦开始（job 已 RUNNING），重入没有意义（claim 会 false 丢弃），且 execute 自身负责终态。
- ack 语义：`claim=false`、`executeExport` 正常返回（内部已落 SUCCESS 或 FAILED 终态）都 `basicAck`；只有 `executeExport` 连终态都落不了而抛出、或解析/claim 重试耗尽，才 `basicNack(requeue=false)`。可沿用现有 `rejectToDlq(channel, deliveryTag)` 私有方法。
- 崩溃窗口（已知、文档化、不做自动恢复）：`claim` 提交后、`executeExport` 终态落定前崩溃 → 消息重投 → 新消费者 `claim` 0 行 → ack 丢弃 → job 停在 RUNNING。这正是 R9 所说的"卡死 RUNNING"边界，本期只记日志不恢复（注释里写明留给后续阶段）。
- **结构性杜绝"多条先置 RUNNING 再执行"**：`prefetch=1` 保证每个消费者同一时刻最多 1 条在途；`concurrency=2` 只是两个线程各持 1 条。任何代码不得在单条消息执行完成前继续 ack/领取下一条。

### 终态回写（`finalize`，两处同一事务）

```text
@Transactional
finalize(jobId, ExportJobStatus 终态, long processed, String errorMessage):
  UPDATE export_job_attempt
     SET status=终态, finished_at=NOW(), error_message=errorMessage
   WHERE job_id=? AND status='RUNNING'          -- 本任务当前那次执行（attempt_no=1）
  UPDATE export_jobs
     SET status=终态, processed_rows=processed
   WHERE id=? AND status='RUNNING'              -- 状态即版本，防并发
  影响行数任一为 0 → 视为异常（理论不可达），记日志并抛（走调用方兜底）
```

- SUCCESS：`processed=实际写出总数`、`error=null`；FAILED：`processed=最后一次已提交的 processed_rows`（不回填、不重置进度）、`error=截断到 1000 字符的原因`（attempt.error_message 为 VARCHAR(1000)）。
- 若 finalize 也抛（DB 不可用）→ `executeExport` 把原始异常继续抛出 → 消费者 nack→DLQ；job 可能留 RUNNING，属 R9 边界。

## 七、后端改动 C：快照 + 高水位 + keyset 游标批量读取

### 统一范围谓词（单一来源，create 与 execute 共用，防两处漂移）

建议新增一个内部快照载体并让谓词构建只写一处：

- `buildSnapshot` 已把 scope 写成 JSON：`{mode, query:{orderNo,..}, selectedIds?, excludedIds?}`（`export_jobs.scope_snapshot`）。
- 定义解析载体（可放 service impl 内）：
  ```java
  record ExportScopeSnapshot(String mode,
                             ExportCreateRequest.Query query,   // 与创建请求同构；SELECTED 模式为 null
                             List<Long> selectedIds,
                             List<Long> excludedIds) {}
  ```
  用注入的 `ObjectMapper.readValue(scopeSnapshot, ExportScopeSnapshot.class)` 解析（Jackson 可解嵌套 public record `ExportCreateRequest.Query`）。
- 把 `buildScopeWrapper` 收敛为"吃快照字段 → 范围谓词"的单一方法，create 的聚合统计与 execute 的批读取**共用它**：
  - `FILTERED/ALL_EXCLUDE`：`like(orderNo/customerName/phone)`、`eq(status)`、`ge/le(createdAt, startTime/endTime 毫秒转 LocalDateTime)`（字段全可空，空则不加条件）；
  - `SELECTED`：`in(id, selectedIds)`；
  - `ALL_EXCLUDE`：`notIn(id, excludedIds)`（为空则不加，沿现实现）；
  - **不得在谓词层带 id 水位/游标**——那是批读取层的事（见下），保证 create 统计（全量）与 execute（分批）同源同谓词。

### 批读取（keyset 游标）

```java
long lastId = 0L;                 // id 无符号自增从 1 起，>0 即起点
List<Order> batch;
do {
    LambdaQueryWrapper<Order> w = buildScopeWrapper(snapshot);
    w.gt(Order::getId, lastId)
     .le(Order::getId, job.getMaxOrderId())      // 高水位：不导出 max_order_id 之后新增的行
     .orderByAsc(Order::getId)
     .last("LIMIT " + batchSize);                 // batchSize=export.batch-size(默认1000)
    batch = orderMapper.selectList(w);
    if (batch.isEmpty()) break;
    // 把 batch 逐行经列元数据映射为单元格 → writer.writeRow(...)（见第八节）
    lastId = batch.get(batch.size() - 1).getId();
    // 本批全部成功写文件后：UPDATE export_jobs SET processed_rows=processed_rows+本批行数 WHERE id=jobId
    // （继续循环：batch 不满 batchSize 或 lastId>=maxOrderId 即自然结束）
} while (batch.size() == batchSize && lastId < job.getMaxOrderId());
```

- **冻结语义**：`scope_snapshot` 冻结"导出哪些行"（创建时参数）；`max_order_id` 冻结"导到哪为止"（创建时命中最大 id）。导出期间新增行（id 更大）不入文件；新增/更新导致与 scope 不再匹配的既有行，按摘要声明**不考虑**（若实际少导几行，`processed_rows` 以实际写出行数为准，不强制等于 expected_total）。
- 查询任一环抛错（DB 断连、SQL 异常等）→ 该异常向上抛到 `executeExport` 的 catch → finalize FAILED（R3）。
- 读取用 `selectList` 全行即可（单批 1000 行，量小；不必为省列做动态投影，避免动态 SQL 映射复杂度）。

## 八、后端改动 D：SXSSF 流式写 excel

### 依赖

`backend/pom.xml` 新增 `org.apache.poi:poi-ooxml`（含 xmlbeans、SXSSF 所需），版本 5.2.5（在 `<properties>` 声明 `poi.version` 复用）。

### 列元数据与取值（单一白名单来源）

收敛现有 `COLUMN_WHITELIST` 到一处列元数据（如 `export` 包下 `OrderExportColumns` 静态表 / 枚举），同时服务 create 的字段校验与 execute 的表头/取值：

| 列键 | 表头（列表所见） | 单元格类型/格式 |
|---|---|---|
| `orderNo` | 订单号 | 文本（净化后字符串） |
| `customerName` | 客户名称 | 文本（净化后字符串） |
| `phone` | 客户手机号 | 文本（净化后字符串） |
| `amount` | 订单金额 | 数值（`BigDecimal.doubleValue()`，单元格 numeric） |
| `status` | 订单状态 | 文本映射：1→未支付 2→已支付 3→已取消 |
| `createdAt` | 订单创建时间 | 文本 `yyyy-MM-dd HH:mm:ss`（`DateTimeFormatter`，静态线程安全） |

规则：
- 表头顺序 = `export_columns`（用户勾选顺序，保序），每列表头取上表"表头"文案 → 第一行即"正确表头"。
- 数据行每列表格取值同上表；`status` 的文本映射须与前端 `constants/order.ts ORDER_STATUS` 一致（未支付/已支付/已取消），保证导出文件与列表所见一致。
- 数字走 numeric 单元格（可被 Excel 求和）；文本走 string 单元格且经"净化"。

### 单元格值净化（白名单安全过滤）

`String sanitizeCellText(String raw)`（纯函数，可单测）：
1. `null` → `""`；
2. 逐码点扫描：落在"控制/非法 XML"范围（`<0x20` 的全部，含 `\n \r \t`，及 `￿` 等）一律替换为单个空格（避免单元格换行/POI 对非法字符抛错）；
3. 结果非空且**首字符为 `= + - @` 之一**时，前置单引号 `'`（Excel 视为纯文本，防公式/注入）；
4. 返回结果。

应用范围：文本型单元格（orderNo/customerName/phone、status 文案、createdAt 文案）。numeric 单元格不走净化。至少覆盖用例：`"=SUM(A1:A2)"→"'=SUM(A1:A2)"`、`"abcd"→"ab cd"`、`null→""`、`"+86..."→"'+86..."`。（**注意**：若你倾向更严格的"仅保留白名单字符集、其余删除"，属推翻本裁决，需先与需求方对齐；默认按上法——只净化会造成单元格出错/注入的符号，不破坏正文数据。）

### SXSSF 写文件

封装一个小的 `ExcelFileWriter`（或直接在 executeExport 内写，视实现整洁度；建议独立 helper 便于管理 window/dispose），行为：
- `new SXSSFWorkbook(export.sxssf-row-window)`（默认 100 行内存窗口，超出自动落盘；可 `setCompressTempFiles(true)` 减内存）；
- 单 sheet（名字固定安全字符，如 `"订单"`，不含非法字符、≤31 字符）；
- 先写表头行，再逐批写数据行；写完 `workbook.write(FileOutputStream(filePath))` → `close` → `finally workbook.dispose()`（释放 SXSSF 自身临时文件）；
- 文件落点：`<export.file-dir>/export_<jobId>.xlsx`（用 jobId 保证唯一，用户文件名 `export_jobs.filename` 留给后续下载阶段做对外命名，不入路径）。

### executeExport 主流程骨架（事务边界务必如此）

```text
void executeExport(long jobId):
  ExportJob job = selectById(jobId)
  scope  = parse(scope_snapshot)                       // 解析失败 → finalize FAILED
  cols   = parse(export_columns) 校验 ∈ 列白名单        // 解析失败 → finalize FAILED
  filePath = fileDir/export_<jobId>.xlsx
  writer.open(filePath, header(cols))
  long processed = 0
  try:
    writer.writeHeader()
    do keyset 批读（第七节）
       每行 row → writer.writeRow(单元格取值（按列元数据格式化/净化/数值化）)
       每批成功 → UPDATE processed_rows += batch.size；processed 累计
    writer.close()                                     // flush 落盘，保留文件
    finalize(jobId, SUCCESS, processed, null)
  catch (Throwable t):
    writer 安全 close/dispose；best-effort 删除未完成的半成品文件(export_<jobId>.xlsx)
    log.error("导出执行失败: jobId, reason", t)
    try finalize(jobId, FAILED, 已提交的processed, truncate(reason))   // 落不下终态则抛出 → 调用方死信/重投
```

- **成功**：文件完整保留 → job/attempt SUCCESS。
- **任一步失败**：job/attempt FAILED + error_message（含半成品文件清理）。
- 进度/终态都以**独立短事务**提交，绝不用一个长事务包住整个导出过程。

   ```ts
   /** 进度百分比：SUCCESS→100；否则封顶 99（"完成"以状态 tag 表达，避免 RUNNING 误显示 100）。expectedTotal<=0 → null */
   export function exportProgressPercent(p: {
     status: ExportJobStatus;
     processedRows: number;
     expectedTotal: number;
   }): number | null {
     if (p.expectedTotal <= 0) return null;
     const ratio = Math.round((p.processedRows / p.expectedTotal) * 100);
     return p.status === 'SUCCESS' ? 100 : Math.min(99, Math.max(0, ratio));
   }
   ```
   单测（`constants/__tests__/export.test.ts`）：
   - `RUNNING` + `processedRows==expectedTotal` → `99`（关键：封顶不触 100）；
   - `SUCCESS` + 同值 → `100`；
   - `expectedTotal<=0` → `null`；
   - 中间值四舍五入正确、`processedRows=0` → `0`。
3. `pages/export-center/index.tsx`：
   - `resolveExportProgress(job)` 改为基于 `exportProgressPercent({ status, processedRows, expectedTotal })`（删掉对 `actualTotal/progress` 的推导）；
   - "导出实际条数"列改读 `processedRows`（RUNNING 期间即实时递增，终态=实际条数；缺失/0 时照常展示数字）；
   - 进度列照旧 `<Progress percent={p} size="small"/>`，`p==null` 显示 `'-'`。
4. **进度轮询（让进度条"活"起来；本阶段新增、可推翻）**：导出中心现有列表只在挂载/tab/翻页时请求一次，进度不会自动刷新。加轻量轮询：`setInterval(4000)`，仅在 `当前 tab === 'RUNNING'` **或** 当前列表含 `status==='RUNNING'` 行时触发同一次 `fetchExportJobs`；`useEffect` cleanup 清定时器；复用既有 `cancelled` 竞态保护。理由：无轮询则"进度条展示"只是一张不会变的快照。若你判断本期不做自动刷新（纯人工刷新查看亦可），请明确记录该取舍。

## 十二、验收清单

**回归验证（8.0 关键节点，改动前后各跑一次确保未回退）**：
- 幂等：同一 `Idempotency-Key` 同内容重发 → `409 已有相同导出任务`，job/outbox 无重复行；异内容 → `409 幂等值冲突`。
- outbox 同生同灭：创建成功 → `export_jobs` 与 `outbox_events` 同事务各 1 行，`trace_id` 一致。
- dispatcher：新任务 ≤6s `published_at` 回写（`status` 已无，以 `published_at IS NULL` 为准）；停 rabbit 期间创建 → 两表照落、恢复后补投、不改库。
- 多消费者竞争：只一个消费者抢到（attempt 恰 1 行、attempt_count=1）；重复投递同一条消息 → 不重复执行（attempt 不增）。
- trace 贯穿：创建请求日志 → dispatcher → 消费者共享同一 `traceId`。

**DB / 模型**：

## 十三、已拍板的解读（可在实施前推翻）

1. **成功路径终态 = SUCCESS**：整份文件写完落盘即 job/attempt SUCCESS；任何一步出错即 FAILED（R2）。8.0 遗留的"RUNNING 任务"不被本阶段自动恢复（R9）。
2. **outbox 发布判据统一为 `published_at IS NULL`**：删列 + 删索引 + 改 dispatcher 谓词与防重写条件；"未发布 ⟺ published_at IS NULL"取代 8.0 双态不变量（R1）。
3. **快照/水位/游标三件套落点**：scope_snapshot=导出参数冻结；max_order_id=一致性水位；keyset id>lastId & id<=max_order_id 升序分页，批大小默认 1000、SXSSF 行窗口默认 100，均配置化（R3/R4）。
4. **进度推进节奏**：每成功写一批，`processed_rows += 本批行数` 单条 UPDATE 一次并推进 lastId；终态 SUCCESS 时 processed_rows=实际总数；FAILED 保留已提交进度不回填（R5）。
5. **进度分母 = expected_total（创建时统计）**，不考虑导出期间更新/删除导致的行集合变化；`processed_rows/expected_total` 仅供展示，实际导出数以 processed_rows 为准（R7/R10）。
6. **列取值与列表所见一致**：status 文案、createdAt 文本、amount 数值、表头中文列名按勾选顺序；白名单唯一来源收敛为一处列元数据（R6）。
7. **净化规则**：只剔除控制/XML 非法字符（含换行）并给 `= + - @` 开头加单引号防注入；不整体白名单删正文（R7；推翻需对齐）。
8. **ack 移到真实执行终态之后**：claim 短事务 → execute（自保证终态）→ basicAck；仅"终态也落不了 / 解析/claim 重试耗尽"才 nack 进 DLQ。崩溃窗口的"卡死 RUNNING"本期不做自动恢复，文档化留给后续（第六节）。
9. **prefetch=1 + concurrency=2** 并行消费，每消费者同一时刻至多 1 条在途——结构性杜绝"多条先置 RUNNING 再执行"（R8）。
10. **导出文件命名/存放**：`<export.file-dir>/export_<jobId>.xlsx`，jobId 保证唯一、失败删半成品、成功保留；`export_jobs.filename` 留给下载阶段对外命名（YAGNI：本期不存路径、不做下载）。
11. **导出中心自动轮询**：为让进度条可观测新增 4s 轻量轮询（仅 RUNNING 相关时触发）；不想要可推翻，但需记录取舍（第十节第 4 点）。
