## 一、背景与目标

全栈订单导出项目：`frontend/`（React18 + Vite + TS + AntD5 + pnpm，`src/http/request.ts` 为底层 fetch 封装、业务接口另建模块）+ `backend/`（SpringBoot3 + Java21 + MyBatis-Plus + Flyway + RabbitMQ，端口 8080）+ MySQL（`order_db`）+ RabbitMQ。信封统一 `ApiResponse{code,message,data,traceId}`；错误语义：`BizException(status,msg)` 由 `GlobalExceptionHandler` 按真实 HTTP 状态返回 envelope（400/404/409），`IllegalArgumentException` 被同一处理器**映射成 HTTP 200 + code=400**（列表查询语义专用，下载路径**禁用**，见 R4）。

**当前代码事实（可直接读到确认，均为 10.0 落地产物）**：

- 文件落点（V6 布局）：`export.file-dir`（`application.yml` 默认 `./data/export`，docker 注入 `EXPORT_FILE_DIR=/app/data/export` + 命名卷 `export-files`）下每任务独立目录 `root/<jobId>/export.xlsx`（`.tmp` 原子改名发布后的唯一对外产物）。`export_jobs` 列：`... processed_rows / finished_at / file_path(相对 root，形如 "<jobId>/export.xlsx"，仅 SUCCESS) / file_size(字节，仅 SUCCESS) / created_at / updated_at`；`filename` = 用户创建时命名（**现状 trim + 非空 + ≤255 校验，不保证 `.xlsx` 后缀**，本阶段裁决补后缀见 R0）。
- `ExportFileStore`（`export/support/`）：root 构造即绝对+归一化；`taskDir/tmpFile/finalFile/relativePath/resolve`；`resolve(String)` = `root.resolve(relative).normalize()` 后 `startsWith(root)` 判定，越界抛 `IllegalArgumentException("导出文件路径越界, 拒绝: ...")`——**下载入口的越界守卫已就绪，直接复用，不要另写一套路径校验**。
- `ExportJobServiceImpl`：持有 `store`（构造注入，root 取自 `@Value("${export.file-dir:./data/export}")`）；`normalizeFilename`（create 用，见 R0 要改）；无任何文件读取/流式对外方法。
- `ExportJobController`：`POST /api/export-job`（create）、`GET /api/export-job`（list，分页）。返回 `ExportJobVO`（record：`id/filename/exportMode/status/expectedTotal/processedRows/maxOrderId/createdAt/finishedAt`）；`toVO` 已映射 `finishedAt`。**`file_path/file_size` 不在 VO 中（10.0 刻意不进，下载阶段才消费）**。
- `ExportJob` 实体：含 `filename/filePath/fileSize/finishedAt` 等全字段与 getter。
- 部署拓扑：dev = Vite 5173 代理 `/api`→8080；docker = frontend(nginx) `location /api/` 反代 `backend:8080`——**前后端永远同源**，下载响应的 `Content-Disposition` 头前端可直接读，**无需改 `CorsConfig`（不加 exposedHeaders）**。
- 前端导出中心 `frontend/src/pages/export-center/index.tsx`：模块级 `columns` 常量（10 列：任务编号/文件名/导出范围/统计条数/实际条数/状态/进度/创建时间/完成时间/文件大小），`PageTable` 只读分页 + 状态 tab + 4s 轮询（仅含 RUNNING 时）。**目前无任何操作按钮、无"操作"列**。错误提示用 antd 静态 `message`（与订单页一致）。
- 后端测试仅 `ExportFileStoreTest` / `OrderExportColumnsTest` 两组纯单测（无 DB/Rabbit）；前端 vitest 有 `constants/__tests__`、`components/__tests__` 等纯逻辑用例。门禁 = `./mvnw` 编译 + 单测 + `pnpm typecheck/test`，端到端需 docker 全栈。

**本阶段目标**（对 `11.0.md` 三个步骤 + 一条注意事项）：
1. 后端 MVC 下载接口：按 job 定位任务 → 校验状态与文件 → **安全路径校验（复用 `store.resolve`）** → 把**库中 `filename`** 经 `Content-Disposition`（UTF-8 编码）放进响应头 → 流式返回文件字节。
2. 前端导出中心：仅在 `SUCCESS` 行渲染"下载文件"按钮。
3. 前端下载：成功 → `blob` 落盘 + 解析并解码响应头文件名；失败 → 解析 JSON envelope 错误并提示。
4. **只向 SUCCESS 提供正确文件**：PENDING/RUNNING/FAILED、文件缺失、路径异常一律拒绝，半成品/越界路径永不外泄。

**明确本期不做（防越界）**：
- **不做失败重试**（源摘要明示暂不提供）：下载失败、任务 FAILED 均无自动重试入口。
- **不改下载之外的状态/文件机制**：outbox / claim CAS / ack / 死信 / keyset / 原子发布 / 四表职责 / 终态分层全部不动；下载是**纯只读**，不产生任何 DB 写入、不新建列（V6 已备好 `file_path/file_size`）。
- **不做清扫 / 断点续传 / Range / 多版本文件**：一次成功一次全量下载。
- **不做历史遗留文件迁移**：phase10 之前的旧 flat 任务在库里 `file_path` 为 NULL，下载按"导出文件不存在"处理（404），不去把旧文件搬进新布局。
- **不把路径校验另写一套**：下载唯一入口就是 `store.resolve`，不新增软链追链/白名单字符审计（10.0 已明确威胁面 = DB 存回相对路径被改，startsWith 足矣；担心软链的二次 `toRealPath` 判定仅在确有需要时再加，本期不加）。
- **不改 `CorsConfig`**：同源代理已能读下载响应头。

## 二、源摘要（11.0.md）的裁决修正表

实施前先按此口径理解 11.0.md，摘要中与代码现状冲突/留白/笔误的表述以此为准：

| # | 摘要表述 | 问题 | 裁决口径（本实施按此） |
|---|---|---|---|
| R0 | "通过响应头返回任务请求接口维护的文件名" | 库中 `filename` 现状**不保证带 `.xlsx` 后缀**（前端弹窗只收裸名、无自拼），若下载直接原样返回，用户没打后缀时拿到的文件名无扩展名 | **下载文件名 = 库中 `filename` 原样（经 Content-Disposition 编码传递，不回填不重拼）。为让"原样"即带 `.xlsx`，在 create 侧兜底**：`normalizeFilename` 改为 trim → 非空 → **若未以 `.xlsx`（大小写不敏感）结尾则拼接 `.xlsx`** → 再校验最终长度 ≤255。效果：新任务入库/展示/下载名恒以 `.xlsx` 结尾，下载接口零特判直接复用库值。已与需求方确认此口径（"前端发起导出任务请求时，后端响应时填充 .xlsx 后缀；本次下载接口直接使用后端响应头的文件名"）。历史已入库的无后缀 SUCCESS 任务**不回填**（下载原样返回旧名即可，属接受；如库里无历史数据则无感知）。**注意**：文件名不参与 `request_hash`，幂等/重试语义不受该改动影响。 |
| R1 | "确保正确的**加密**正确传递"；前端"**解密**响应头里的文件名" | "加密/解密"疑为"编码/解码"笔误，且易诱导引入加解密 | **= 编码传递**。后端用 Spring `ContentDisposition.attachment().filename(name, StandardCharsets.UTF_8).build()` 由框架生成 RFC 6266/RFC 5987 头：含非 ASCII 时输出 `filename*=UTF-8''<百分号编码>`（可带 ASCII `filename=` 兜底），纯 ASCII 时输出普通 `filename="..."`。**绝不手工拼 `Content-Disposition` 字符串**（防 CRLF 头注入与编码错误——`filename` 来自用户输入，虽经长度校验但未剔除控制字符，只有交给 Spring 编码才安全）。前端对 `filename*` 做 `decodeURIComponent` 解码（"解密"= 百分号解码），并对解码失败做兜底。全程无任何加解密算法。 |
| R2 | "按照 job 查询导出任务的下载地址信息" | "下载地址信息"易被理解为返回一个 URL 字符串 | 裁决：**下载"地址"就是本阶段新增的文件接口本身** `GET /api/export-job/{id}/download`（直接流式返回文件字节），不设计"先生成 URL、前端再拉取"的两跳方案（无鉴权系统、文件就在受控 root，多一跳纯属过度设计）。 |
| R3 | "下载地址要经过安全路径校验" | 校验放哪、用什么判据留白 | 服务端定位文件时经 `store.resolve(job.getFilePath())`（10.0 已落地：`normalize` + `startsWith(root)`，越界抛 `IllegalArgumentException`）。**这是唯一守卫**，下载 serving 的绝对路径必须由它产出，绝不能拿 `file_path` 直接拼 `Path.of` 去读。 |
| R4 | "只向前端提供 SUCCESS 状态的正确文件" | 非 SUCCESS / 文件缺失 / 路径被改 三种拒绝的 HTTP 语义与信封形态未定义 | 三种拒绝全部走 `BizException`（真实 HTTP 状态 + envelope JSON，前端能统一按 JSON 错误解析）：① job 不存在 → **404**"导出任务不存在"；② `status != SUCCESS` → **409**"任务尚未成功导出，暂不可下载"（PENDING/RUNNING/FAILED 统一此分支，半成品不外泄，对齐注意事项 1）；③ `file_path` 为空 / `store.resolve` 越界 / 文件不存在或非普通文件 → **400/404**（越界 400"导出文件路径越界…"，缺失 404"导出文件不存在…"，二者可按实际分支给文案）。**关键坑：下载路径内任何"状态/参数异常"都不得抛裸 `IllegalArgumentException`**——它会被 `GlobalExceptionHandler` 映射成 **HTTP 200 + code=400**，下载客户端会误判成功去存一个错误 body。因此 `store.resolve` 的 `IllegalArgumentException` 必须在 service 里捕获并翻译成 `BizException(400, ...)` 再抛。 |
| R5 | "成功时使用 blob 下载文件，校验并解码响应头里的文件名；失败时校验 json 错误信息" | 复用 `request.ts` 会默认 `res.json()`，无法下载二进制；"校验 json"指哪一层 | 前端**用裸 `fetch`（不走会读 JSON 的 `request()`）**请求该接口：`res.ok` → `await res.blob()` + 从 `res.headers.get('Content-Disposition')` 解析文件名（优先 `filename*` 解码，回退普通 `filename=`）；`!res.ok` → 解析 body 为 envelope JSON，抛 `ApiError`（message 用后端原文），**body 非 JSON（如网关/容器层错误）降级为 `ApiError(HTTP <status>)`**。文件命中浏览器保存用 `URL.createObjectURL + <a download>` 触发，随后 `revokeObjectURL`。 |

## 三、后端改动 A：create 文件名兜底 `.xlsx`（R0）

仅改 `ExportJobServiceImpl.normalizeFilename`（create 路径，`private` 方法，签名的返回类型不变，仍是规范化后的入库/展示名）：

```java
private String normalizeFilename(String filename) {
    String name = filename == null ? "" : filename.trim();
    if (name.isEmpty()) {
        throw new BizException(400, "文件名不能为空");
    }
    if (!name.toLowerCase(Locale.ROOT).endsWith(".xlsx")) {
        name = name + ".xlsx";          // R0：新任务入库名恒带 .xlsx，下载头原样复用
    }
    if (name.length() > 255) {
        throw new BizException(400, "文件名长度不能超过 255");
    }
    return name;
}
```

要点：
- 只影响 create 入库值与 `ExportJobVO.filename`（创建响应 + 导出中心展示即带后缀，属接受的口径）；不影响 `request_hash`（不含 filename）→ 幂等/重试完全不受影响。
- 已入库历史行不回填；`filename` 仍只是"对外展示/下载名"，**永不进入文件路径**（磁盘名仍是 `root/<jobId>/export.xlsx`，两者本就解耦，勿混）。
- 无 DB 迁移、无实体/VO 改动。

## 四、后端改动 B：service 层下载定位与校验（R3/R4）

### 接口 `ExportJobService`

加一个方法与一个承载返回的嵌套 record（不新增独立文件；该 record 不是 JSON DTO，仅 service→controller 的内部载体，嵌在接口里隐式 public static 最省）：

```java
/**
 * 下载源（已通过全部校验）：file 为 store.resolve 之后的绝对路径（已在受控 root 内），
 * filename 为库中展示名（R0 起恒 .xlsx 结尾），供 controller 填 Content-Disposition。
 */
record DownloadSource(Path file, String filename) {
}

/**
 * 下载前的定位与校验（只读，不落任何状态）。
 * 仅 SUCCESS 提供；其余状态/文件缺失/路径越界一律抛 BizException（真实 4xx + envelope），
 * 由调用方（controller）流式返回文件。
 *
 * @param jobId export_jobs.id
 * @return 越界校验后的文件绝对路径 + 对外文件名
 */
DownloadSource downloadSource(long jobId);
```

### 实现 `ExportJobServiceImpl`

在类里补 `downloadSource`，注意 `store.resolve` 的 `IllegalArgumentException` 必须翻译成 `BizException`（R4 的坑），不要让它漏到全局处理器变 200+code=400：

```java
@Override
public DownloadSource downloadSource(long jobId) {
    ExportJob job = exportJobMapper.selectById(jobId);
    if (job == null) {
        throw new BizException(404, "导出任务不存在");
    }
    if (!ExportJobStatus.SUCCESS.name().equals(job.getStatus())) {
        // PENDING / RUNNING / FAILED 一律拒绝：半成品/失败产物不外泄
        throw new BizException(409, "任务尚未成功导出，暂不可下载");
    }
    String filePath = job.getFilePath();
    if (!StringUtils.hasText(filePath)) {
        throw new BizException(404, "导出文件不存在");
    }
    Path file;
    try {
        file = store.resolve(filePath);          // ★ 唯一守卫：normalize + startsWith(root)，越界抛
    } catch (IllegalArgumentException e) {
        throw new BizException(400, e.getMessage());   // 勿让裸 IllegalArgumentException 漏出（见 R4）
    }
    if (!Files.isRegularFile(file)) {
        throw new BizException(404, "导出文件不存在，可能已被清理");
    }
    return new DownloadSource(file, job.getFilename());
}
```

要点：
- 顺序刻意如此：先存在性/状态，再 `file_path` 空校验，再 `resolve` 越界守卫，最后才 `isRegularFile`——任何分支都不会拿未校验路径去碰磁盘。
- **不加 `file_size` 一致性校验**：磁盘文件发布后只读不改，size 与库值恒一致；真要下发 Content-Length 让 controller 用 `resource.contentLength()` 即可（见 B），不必把 size 带回。
- 全程只读：无 UPDATE、无事务、不碰 outbox/attempt/消费者。

## 五、后端改动 C：下载接口（controller）

`ExportJobController` 加 endpoint。用 Spring `FileSystemResource` + `ResponseEntity<Resource>` 流式返回（大文件不整读进内存）；`Content-Disposition` 交给 `ContentDisposition.attachment().filename(name, UTF_8)` 生成（R1）；Content-Length 用 `resource.contentLength()`（FileSystemResource 读的是文件实际长度），读取异常包成 `BizException(500)`：

```java
/** 下载成功导出文件：GET /api/export-job/{id}/download，仅 SUCCESS 任务有正确文件 */
@GetMapping("/{id}/download")
public ResponseEntity<Resource> download(@PathVariable("id") Long id) {
    ExportJobService.DownloadSource src = exportJobService.downloadSource(id);   // 定位 + 状态 + 越界校验（已收敛为 BizException）
    FileSystemResource resource = new FileSystemResource(src.file());
    HttpHeaders headers = new HttpHeaders();
    headers.setContentType(MediaType.parseMediaType(
            "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet"));
    // R0/R1：下载名 = 库中 filename 原样；编码交给 Spring 生成 filename*/filename（绝不手拼，防 CRLF/乱码）
    headers.setContentDisposition(
            ContentDisposition.attachment().filename(src.filename(), StandardCharsets.UTF_8).build());
    long length;
    try {
        length = resource.contentLength();
    } catch (IOException e) {
        throw new BizException(500, "读取导出文件失败");
    }
    return ResponseEntity.ok().headers(headers).contentLength(length).body(resource);
}
```

要点：
- 路径变量 `Long id`：传非数字 id 会命中 Spring 类型转换的 400（默认响应、非 envelope）——前端下载失败分支已做"body 非 JSON 降级报错"，可接受；若想统一 envelope 再补一个转换异常处理器，**本期不做**。
- 不设置 `Content-Type: application/octet-stream` 兜底：xlsx MIME 即可，前端按 blob + download 属性落盘，不依赖 MIME 判断。
- **不改 `CorsConfig`**：dev/docker 都同源代理，`Content-Disposition` 前端可直接读（见背景部署拓扑）。不要为"以防将来跨域"去加 `exposedHeaders`。
- 全局异常处理器/信封工具零改动：三种拒绝已在 service 收敛为 `BizException` → 既有处理器按真实状态返回 envelope JSON。

## 六、前端改动 A：下载名解析与触发落盘（纯函数 + DOM 工具）

新增 `frontend/src/utils/download.ts`：

```ts
/** 解析 Content-Disposition：优先 filename*=UTF-8''<百分号编码>（decodeURIComponent 解码），
 *  回退普通 filename="..."；无该头/无法解析返回 null。解码失败也回退普通 filename，避免吞掉可读名。 */
const STAR_PATTERN = /filename\*\s*=\s*UTF-8''([^;]+)/i;
const FALLBACK_PATTERN = /filename\s*=\s*"([^"]*)"/i;

function percentDecode(value: string): string | null {
  try {
    return decodeURIComponent(value);
  } catch {
    return null; // 畸形百分号序列
  }
}

export function parseDownloadFilename(contentDisposition?: string | null): string | null {
  if (!contentDisposition) return null;
  const star = STAR_PATTERN.exec(contentDisposition);
  if (star) {
    const decoded = percentDecode(star[1]);
    if (decoded != null) return decoded;
  }
  const plain = FALLBACK_PATTERN.exec(contentDisposition);
  return plain ? plain[1] : null;
}

/** 把 blob 以指定文件名触发浏览器保存并立即释放对象 URL */
export function saveBlob(blob: Blob, filename: string): void {
  const url = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url;
  a.download = filename;
  document.body.appendChild(a);
  a.click();
  a.remove();
  URL.revokeObjectURL(url);
}
```

（`parseDownloadFilename` 是纯函数、可单测；`saveBlob` 是唯一碰 DOM 的地方，保持页面薄。）

## 七、前端改动 B：复用错误解析 + 下载请求

### `frontend/src/http/request.ts`：导出一个供"非 JSON 成功响应"接口（如下载）复用的错误解析

现状 `request()` 内联了解析逻辑、`isEnvelope` 为私有。加一个导出函数，让下载失败走与列表/创建完全一致的 `ApiError`（含 envelope code/message/traceId 与 body 非 JSON 时的降级）：

```ts
/** 解析失败响应的 envelope（供下载等非 JSON 接口复用）；body 非 JSON 时降级为 ApiError(HTTP status) */
export async function toApiError(res: Response): Promise<ApiError> {
  try {
    const body = await res.json();
    if (isEnvelope(body) && body.code !== 0) {
      return new ApiError(body.message || '请求失败', {
        httpStatus: res.status,
        code: body.code,
        traceId: body.traceId,
      });
    }
  } catch {
    // body 非 JSON（网关/容器错误）→ 落入下方降级
  }
  return new ApiError(`请求失败：HTTP ${res.status}`, { httpStatus: res.status, code: res.status });
}
```

### `frontend/src/http/export.ts`：下载函数（裸 fetch，不走会读 JSON 的 `request()`）

```ts
import { toApiError } from './request';
import { parseDownloadFilename } from '../utils/download';

export interface DownloadResult {
  blob: Blob;
  /** 后端 Content-Disposition 解析出的文件名；头缺失时为 null（调用方用行数据 filename 兜底） */
  filename: string | null;
}

/** 下载导出文件：成功→blob + 解析文件名；失败→解析 envelope 抛 ApiError（后端 message 原文） */
export async function downloadExportJob(id: number): Promise<DownloadResult> {
  const res = await fetch(`/api/export-job/${id}/download`);
  if (!res.ok) {
    throw await toApiError(res);
  }
  const blob = await res.blob();
  return { blob, filename: parseDownloadFilename(res.headers.get('Content-Disposition')) };
}
```

   ```tsx
   }
   ```

## 十、验收清单

**后端（docker 全栈 `up -d --build` 后，造一个成功导出任务取到其 `<id>`，以下用 curl 打）**：
- SUCCESS 任务下载：
  - `curl -sD /tmp/h.txt -o /tmp/dl.xlsx 'http://localhost:8080/api/export-job/<id>/download'`：
    - 响应行 `HTTP/1.1 200`；`Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`；
    - `Content-Disposition` 含 `filename*=` 且按 UTF-8 编码（任务名含中文时断言存在 `filename*=UTF-8''`，`decodeURIComponent` 后 == 库中 `filename`）；纯 ASCII 名至少能解析出普通 `filename="..."`；
    - `Content-Length` == 库中 `file_size`（`ls -l` 比对）；`/tmp/dl.xlsx` 能 `unzip -t` 通过、`sha256sum` 与 `root/<id>/export.xlsx` 一致；
  - **只读性回归**：下载前后该 job 行字段（status/processed_rows/file_path/file_size）与 outbox/attempt 均无变化。
- **拒绝分支（三种都断言真实 HTTP 状态 + envelope JSON，body 是 `ApiResponse{code,message,...}` 非文件）**：
  - `FAILED` / `PENDING` / `RUNNING`（RUNNING 可用大任务趁导出中打）任务 → `409`，message 含"尚未成功导出"；
  - 不存在的 `<id>`（如 999999）→ `404`"导出任务不存在"；
  - 手工 `UPDATE export_jobs SET file_path='../../etc/passwd' WHERE id=<SUCCESS id>` → 下载 → `400`"导出文件路径越界…"，**绝不能返回系统文件内容**；
  - 把 SUCCESS 任务文件从卷里移走/改名后下载 → `404`"导出文件不存在"。
- **R0 回归**：create `filename="订单"` → 响应含 `filename:"订单.xlsx"`；重复同内容（幂等）仍 409 duplicate 且不因后缀改动漂移（文件名不入 hash）；导出中心列表展示名带 `.xlsx`。

**前端**：
- vitest：`parseDownloadFilename` —— ① 含 `filename*=UTF-8''<订单导出.xlsx 百分号编码>` → 解码后 `"订单导出.xlsx"`；② 纯 ASCII `filename="orders.xlsx"` → `"orders.xlsx"`；③ 无该头/传 null → `null`；④ star 段畸形百分号（解码抛错）→ 回退普通 `filename`。

## 十一、已拍板的解读（可在实施前推翻）

1. **下载名 = 库中 `filename` 原样**（经 Content-Disposition 编码传递）；为使原样即带后缀，create 的 `normalizeFilename` 无 `.xlsx` 结尾时统一补上（用户拍板：前端发起导出任务请求时，后端响应即带 `.xlsx`；下载接口直接使用该响应头文件名）。文件名不入路径、不入 request_hash（R0）。
2. **"加密/解密" = 编码/解码**：后端 `ContentDisposition.attachment().filename(name, UTF_8)`，前端对 `filename*` 做 `decodeURIComponent`；全程无加解密（R1）。
3. **下载"地址"就是文件接口本身** `GET /api/export-job/{id}/download`，不做两跳 URL（R2）。
4. **路径守卫复用 `ExportFileStore.resolve`**，下载唯一入口；`resolve` 的 `IllegalArgumentException` 翻译成 `BizException(400)`，**绝不漏到全局处理器变 HTTP 200 + code=400**（R3/R4）。
5. **只向 SUCCESS 提供文件**：404 不存在 / 409 非成功 / 400 路径异常 / 404 文件缺失，全部真实 HTTP 状态 + envelope JSON（R4）。
6. **前端**：SUCCESS 行才渲染按钮；裸 fetch → blob + `Content-Disposition` 解析（`filename*` 优先、普通 `filename` 回退）；失败解析 envelope 抛 `ApiError`、body 非 JSON 降级；`message` 提示后端原文（R5）。
7. **下载纯只读**：不落任何状态、不改 outbox/claim/ack/死信/文件机制；不做失败重试 / 清扫 / Range / 断点续传 / 历史迁移 / CORS 改动。

请遵循极简原则，优先复用现有代码（`store.resolve` 守卫、`BizException`/`GlobalExceptionHandler`、`request.ts` 的 `ApiError` 与信封解析、导出中心既有表格与 `message` 用法）与原生方案（`FileSystemResource` 流式、`URL.createObjectURL`），不引入新依赖，不越上面"不做"清单。
