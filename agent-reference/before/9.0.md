本阶段需求摘要
异步导出任务的前后端已打通，前端在导出中心也能查到对应的 PENDING 状态导出任务信息，消息队列也打通，能完成订单从 PENDING -> RUNNING 状态的正确流转。本阶段完成消费者领取消息后，执行 excel 文档的生成，本阶段暂不开放后续的用户操作

## 优化部分
- 前端部分
    1. 导出任务请求参数优化，“导出已选”的2种场景：手动勾选、全选反选，2种场景的请求参数，id数组升序排序后再传到后台

- 后端部分
    1. outbox_events表，无需提供 status字段（与 published_at 重复了，而且没实际逻辑操作，让程序变复杂了）

## 本期目标
1. 先验证前面阶段做的逻辑是否符合以下关键节点的要求：
    - 导出任务申请从前端发起，前端在请求头携带幂等值，后端响应http请求后，获取幂等值信息，数据库建有唯一索引，然后判断是否有相同的幂等值，完成入库或者驳回的动作。
    - 设计的 outbox模式，保证了正常的请求动作，同时写入 order表和 outbox_events表（失败时都驳回）
    - dispatcher 定时扫描 outbox_events表，根据要求取出符合的job，投递到 queue队列中（必须有消息确认才可更新表中的 published_at 字段，否则不动）
    - 存在多个消费者竞争 queue队列中的消息，保证只有一个消费者能抢到（消费者执行语句后未能抢到的消息，丢弃即可）
    - 新加入的动作：消费者往下执行生成excel文件的动作，完成后执行 basicAck 完成消息的出列。（不存在消费者先把多条消息都设置为 RUNNING，再等待执行）

2. RabbitMQ
    - prefetch 设置为1，设置2个消费者并行

3. 使用快照+高水位+游标分页的形式，批次读取数据库信息
    - 批量读取的窗口设置为 1000 条
    - 快照为异步导出任务请求，带来的查询参数（已提前预设数据库字段信息）
    - 高水位表示当前导出任务最大的id信息，保证异步导出动作，不会因为有新增的信息导致导出信息不正确（暂不考虑更新或者删除导致的数据不匹配）
    - 游标分页 keyset 表示每次的 lastId
    - 若查询失败时，整个导出动作设置为失败，并正确回写数据库状态，将job状态流转至 failed

4. 使用 SXSSF 流式写入 excel 的形式，生成文件
    - 根据导出选择的 column 生成第一行正确的表头
    - SXSSF 插件写入文件可操作对象的窗口设置为 100，避免内存溢出风险
    - export_jobs表增加导出进度的相关字段（当前导出条数 processed_rows）， 每次成功写入文件后，正确的更新数据库信息，才推进批次查询的进度
    - 针对数据值进行白名单安全过滤，避免特殊符号写入 excel 文件导致单元格出错
    - 本阶段暂不提供下载和最终文件生成，保留临时文件，如有哪一个环节出现错误，整个动作设置为失败，将job状态流转至 failed

5. 前端加入进度条展示，（processed_rows / 预计总数），保证最大进度百分比只到 99%
