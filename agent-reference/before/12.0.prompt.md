## 一、背景与目标

全栈订单导出项目：`frontend/`（React18 + Vite + TS + AntD5 + pnpm）+ `backend/`（SpringBoot3 + Java21 + MyBatis-Plus + Flyway + RabbitMQ，端口 8080，`@EnableScheduling` 已开）+ MySQL（`order_db`）。信封 `ApiResponse{code,message,data,traceId}`；`BizException(status,msg)` → `GlobalExceptionHandler` 按真实 HTTP 返回 envelope；裸 `IllegalArgumentException` 会被映射成 **HTTP 200 + code=400**（列表查询语义专用，**任务动作类接口禁用**，见 R1/R4 的坑）。

**当前代码事实（可直接读确认）**：

- 任务主表 `export_jobs`（V2+V5+V6）：`id / idempotency_key(uk) / request_hash / export_mode / status(PENDING/RUNNING/SUCCESS/FAILED) / filename / export_columns / scope_snapshot / expected_total / max_order_id / processed_rows / finished_at / file_path / file_size / created_at / updated_at`。**乐观锁一直用"状态即版本"（`WHERE id=? AND status=?`），无独立版本列**（本阶段新增 `job_version`，见 R0）。
- `outbox_events`（V3+V4）：`id / job_id(uk, 1任务=1事件) / trace_id / published_at / attempt_count / created_at / updated_at`。未发布判据 `published_at IS NULL`；`attempt_count`=消费者成功领取次数，**恒等于该任务 `export_job_attempt` 行数、恒等于每次执行的 `attempt_no`**。
- `export_job_attempt`（V3）：`id / event_id / job_id / attempt_no(uk: job_id+attempt_no) / status(RUNNING/SUCCESS/FAILED) / started_at / finished_at / error_message / created_at`。一行=一次执行；执行结束回填终态后**永不再 UPDATE**（归档语义）。
- `ExportJobServiceImpl`：`claim(eventId,jobId)` = CAS `PENDING→RUNNING` 同事务内 outbox `attempt_count+1` + insert 一条 RUNNING attempt（`attempt_no=attempt_count`）；`executeExport(jobId)` = selectById → 读快照/列 → `writeBatches`（每批成功后**无守卫** `SET processed_rows += 批行数` 的独立短事务推进，见代码 292-295 行）→ close `.tmp` → `publishAtomically` 改名发布 → `finalizeJob(SUCCESS, …写 file_path/file_size/finished_at/processed_rows)`；catch Throwable → `disposeQuietly` + `store.deleteTaskDir(jobId)` + `finalizeJob(FAILED, …)`。`finalizeJob` 用注入 `TransactionTemplate` 包**两处 UPDATE**（`executeExport` 同类自调用，勿改回 `@Transactional`——phase9 第五节的坑），attempt 按 `job_id AND status='RUNNING'`、job 按 `id AND status='RUNNING'` 定位，0 行即抛 `IllegalStateException`。
- `ExportFileStore`（`export/support/`）：`taskDir/tmpFile(=export.xlsx.tmp)/finalFile(=export.xlsx)/relativePath(=jobId/export.xlsx)/resolve(越界守卫)/deleteTaskDir(整目录 best-effort 递归删)`。**`deleteTaskDir` 已就绪，孤儿清扫直接复用，不要另写文件遍历**。
- `OutboxDispatcher`：`@Scheduled(fixedDelay=5000)` 扫 `published_at IS NULL` → 投递 → confirm 无 return 回写。`ExportJobConsumer`：manual ack + 方法内 RetryTemplate(5) + 显式 `basicNack`→DLX；**已知崩溃窗口（phase9 文档化，未自动恢复）：claim 提交后、终态落定前崩溃 → job 停在 RUNNING**——这正是本阶段心跳租约要收的口子。
- 下载（11.0）：`GET /api/export-job/{id}/download`，`downloadSource` 顺序 = 存在性 → `status==SUCCESS` 否则 409 → `file_path` 非空 → `store.resolve`（IllegalArgumentException 翻译 `BizException(400)`）→ `Files.isRegularFile` 否则 404。**EXPIRED 尚未存在，本阶段在此方法加一个分支（R2）**。
- `ExportJobController`：`POST /api/export-job`（create）、`GET /api/export-job`（list）、`GET /{id}/download`。`ExportJobVO` record（含 `finishedAt`，**无 file 两列、无 jobVersion**）；`toVO` 是唯一映射点。
- 前端导出中心 `frontend/src/pages/export-center/index.tsx`：模块级 `columns`（含"操作"列，**仅 SUCCESS 行渲染"下载文件"**，下载是纯动作故处理器也在模块级）；`load` 整表 `setList(result.list)` 替换 + 请求取消防竞态；轮询 `shouldPoll = statusTab==='RUNNING' || hasRunning || list 含 RUNNING 行`（**不含 PENDING**，R-F 要改）；常量 `constants/export.ts`：`EXPORT_JOB_STATUS{text,color}` + `EXPORT_JOB_STATUS_TABS`（全部+PENDING+RUNNING+SUCCESS+FAILED）；`exportProgressPercent` SUCCESS→100 否则封顶 99。类型 `types/order.ts`：`ExportJobStatus`（无 EXPIRED）、`ExportCenterJob extends ExportJobVO`。
- 调度现状：`@EnableScheduling` + `OutboxDispatcher` 一个 `@Scheduled` 任务，**默认单线程调度器**（`spring.task.scheduling.pool.size` 未配）——本阶段再加 2 个扫描任务后要配池，见 R7。
- 门禁 = `./mvnw` 编译 + 后端单测 + `pnpm typecheck/test`；端到端 docker 全栈。后端现仅 `ExportFileStoreTest`/`OrderExportColumnsTest` 两组纯单测；前端 vitest 纯逻辑用例。

**本阶段目标**（对 `12.0.md` 四步 + 两条注意事项）：

1. **防倒退**：新增 `job_version` 写序号 + 全量回写守卫，堵"旧 attempt/旧 worker 信息错误覆盖新 attempt"，并为后续 SSE 进度推送铺字段（**本期不实现 SSE**，R0）。
2. **FAILED 重试**：仅 FAILED 可重试；重试 = 重入 outbox 推进，旧 attempt 归档不可改；前端失败行出"重试"按钮。
3. **EXPIRED**：SUCCESS 文件生成 24h 后过期；每小时扫描，先删文件再置 EXPIRED。
4. **孤儿文件/卡死 RUNNING**：心跳 + 租约（5min），RUNNING 无租约或过期 → 两张表同事务置 FAILED + 删本任务目录。

**明确本期不做（防越界，逐条核）**：
- **不做 redis / SSE**（源摘要明示；SSE 只在本阶段把 `job_version` 字段与"只接受更大版本"的合并契约落好，见 R0/R-F）。
- **不做自动重试**：租约回收只置 FAILED，不自动重投 outbox；重试一律人点"重试"入口（R1）。
- **不新建独立重试队列/交换机**：重试复用同一 outbox 行（`uk_job_id` 本就 1 任务 1 事件），靠既有 5s dispatcher 重投（R1）。
- **不为"孤儿清扫"另建独立扫描**：12.0 第 4 步的两条"已完成场景"（原子生成失败的 `.tmp` 删除、未登记 `.xlsx` 删除）由"既有 catch 的 `deleteTaskDir` + Stale 静默退出只删己 tmp + 租约回收 `deleteTaskDir`"三点天然覆盖（R6），不写第五个调度器。
- **不给 attempt 表加 job_version 列**：attempt 是每执行一条、终态后只读的归档，其排序/隔离已有 `attempt_no`；版本号是 job 行快照的排序依据，只在 jobs（R0）。
- **不改 outbox 判据 / ack / 死信 / claim 基本 CAS / `resolve` 守卫 / `.tmp`→原子发布 / `ExportFileStore` 布局根**。
- **不做 409 语义外的幂等兜底 / DLQ 自动重放 / Range / 断点续传 / 历史文件迁移 / 过期文件二次下载**。
- **不新增"已过期"状态 tab**（非源需求；EXPIRED 行在"全部"可见即可，R-F）。

## 二、源摘要（12.0.md）的裁决修正表

实施前先按此口径理解 12.0.md。与代码现状冲突/留白/易误导处以此为准：

| # | 摘要表述 | 问题 | 裁决口径（本实施按此） |
|---|---|---|---|
| R0 | "export_jobs / export_job_attempt 两表都加 job_version；每次任务开始执行时从 1 计算；每次成功写入文件回写状态时先扫出当前值、递增的形式加载进新动作" | ①"每次成功回写状态时递增"其实点出了正确机制，但"两表都加 + 每次开始从 1 计算"与其自相矛盾：若每次执行版本从 1 重算，跨重试会出现重复版本号，读者/SSE 无法据此判断新旧（本阶段正是要拿它当全 job 生命周期的单调写序号）；②attempt 表每行只属于一次执行、终态后只读，加版本列冗余（已有 attempt_no） | **只在 `export_jobs` 加 `job_version`（BIGINT NOT NULL DEFAULT 0），语义 = 该 job 的单调写序号，本 job 全生命周期永不归零、只增不减**。**凡是把 export_jobs 往前推进一次的状态/进度写入，都做 `job_version = job_version + 1`**：claim(RUNNING)、每批进度(`processed_rows += 批数`)、finalize 终态(SUCCESS/FAILED)、重试(PENDING 且 processed_rows 归零)、租约回收(FAILED)、过期回收(EXPIRED)。用途有二：(a) **乐观锁 CAS**——活跃 worker 每批/终态写回都带 `WHERE id=? AND job_version=<worker 预期> AND status='RUNNING'`，见 R4；(b) **快照事件序号**——读者/轮询看到"版本更大=更新"，为后续 SSE push 的排序铺字段（本期只落字段与契约，不实现 SSE）。attempt 表不加列。摘要"每次任务开始执行时从 1 计算"由 attempt_no 表达（每次执行一个自增号），`job_version` 恒单调。 |
| R1 | "仅 FAILED 允许重试；前端触发重试重新进入 outbox 模式推进，旧 attempt 归档保留不允许修改" | ① 重试入口的 HTTP/校验语义、重试与 dispatcher/claim 的衔接留白；②"重试"与"旧 attempt 不可改"如何落地需落到状态转换 | **重试 = 仅 `FAILED` 可点**：`POST /api/export-job/{id}/retry`（无 body）。同事务：job `FAILED→PENDING` 且 `processed_rows=0`（重跑从 0 计，旧进度不并入新执行）且 `job_version+1`（让 FAILED 之后的 PENDING 成为"更大版本"的新快照，前端才能识别新执行）；同一 outbox 行 `published_at→NULL`（`uk_job_id` 决定只能复用这一行）；随后由既有 5s dispatcher 重投 → 消费 claim CAS `PENDING→RUNNING` 并再次 `job_version+1` → 开**新 attempt**（`attempt_no = attempt_count+1`）。旧 FAILED attempt 行保持原样（含 started/finished/error_message）=归档，任何代码不 UPDATE 已终态 attempt（见 R4）。接口语义：job 不存在 404；`status != FAILED`（SUCCESS/RUNNING/PENDING/EXPIRED）→ 409 "仅失败状态的任务可重试"（并发双击第二次命中此 409，天然幂等）。成功返回 200 + 新 VO（status=PENDING, processedRows=0, jobVersion 已 +1）。**重试与下载一样：状态异常一律 `BizException` 真实 HTTP + envelope，绝不抛裸 `IllegalArgumentException`**。 |
| R2 | "仅 SUCCESS 流转 EXPIRED；成功生成时记录过期时间=成功 24h 后；每小时扫超时 SUCCESS，先删文件再置 EXPIRED" | ① 过期时间落哪个字段、谁写入未定；② EXPIRED 后下载/前端语义未定（11.0 下载只认 SUCCESS） | **`export_jobs` 加 `expires_at`**：SUCCESS 落终态时（`finalizeJob` 同一 UPDATE）写 `expires_at = finished_at + 24h`（TTL 取配置 `export.expire-hours`，默认 24）。每小时间隔扫描 `status='SUCCESS' AND expires_at <= NOW()`（分批 LIMIT）→ **先 `deleteTaskDir(jobId)` 再置 `EXPIRED`（置状态时 `job_version+1`）**（顺序照摘要；置状态放最后，天然防"已删文件仍被下载/再展示"）。V7 一并**回填存量 SUCCESS**：`UPDATE export_jobs SET expires_at = finished_at + INTERVAL <expire_hours> HOUR WHERE status='SUCCESS' AND expires_at IS NULL`（同一迁移写死 24h 即可，与默认一致）。**下载**：`downloadSource` 在"非 SUCCESS 一律 409"前加 EXPIRED 分支 → `BizException(404, "导出文件已过期清理…")`（文件已删，走 404 语义而非 409，与 11.0"文件缺失 404"同族）；EXPIRED 行前端状态列展示"已过期"，**不渲染下载/重试按钮**。EXPIRED 不可再重试、不可再下载。24h 边界内、扫描尚未跑的空窗（分钟级）仍 SUCCESS 可下载——接受，不额外在 downloadSource 做 `expires_at<=now` 预判（扫描是唯一回收口）。 |
| R3 | "加心跳时间 + 租约时间（=心跳+5min），两字段同步往前写；扫 RUNNING 无租约或过期 → FAILED + 删临时文件" | ① 字段放哪表、要不要存冗余列；② 扫描判据与翻 FAILED 时两张表怎么处理 | **两列都写在 `export_jobs`（冗余可读，照摘要字面）**：`heartbeat_at`（最近一次证明存活的操作时间）+ `lease`（截止时刻 = 该次心跳 + 租约秒数，随心跳同步写）。放 jobs 的理由：每次写批推进进度的那个 UPDATE **顺带把两列一起 SET**（`heartbeat_at=NOW(), lease=DATE_ADD(NOW(), INTERVAL n SECOND)`），心跳零额外 DB 写（放 attempt 则每批多一次对第二张表的写）；扫描谓词单表直接扫 `export_jobs`。attempt 表维持纯执行动作记录，不加心跳。**claim 命中时重置两列**（新 attempt 拿全新租约）。租约秒数取配置 `export.lease-seconds` 默认 300。**租约回收**：`@Scheduled(fixedDelay=60_000)` 扫 `status='RUNNING' AND (lease IS NULL OR lease < NOW())`（`lease IS NULL` 覆盖迁移时残留在跑/从未心跳的行）→ 对每行**同一事务**做两处 UPDATE：`export_job_attempt SET status='FAILED', finished_at=NOW(), error_message='执行租约过期(心跳停止),由扫描回收' WHERE job_id=? AND status='RUNNING'` + `export_jobs SET status='FAILED', heartbeat_at=NULL, lease=NULL, job_version=job_version+1 WHERE id=? AND status='RUNNING'`（CAS 防与真实终态竞争）；事务落定后 `store.deleteTaskDir(jobId)`（删遗留 `.tmp` 与"已发布未回写"的 `.xlsx`）。**只置 FAILED，不重投 outbox**（新执行由人点重试触发）。 |
| R4 | "每一个环节都判断是否有联动反应"（注意事项）+ 防倒退回写 | "联动"具体化为：进度/终态回写在多 attempt 并存/易主时如何不误写 | **守卫矩阵（本次最关键的落点，务必全对齐）**：活跃 worker 在 execute 开始时读 `startSeq = job.jobVersion`（=claim 之后的版本号），并维护本地预期号 `seq`（初值 startSeq）。两类写回统一加守卫——① 每批进度 UPDATE：`SET processed_rows=processed_rows+批数, heartbeat_at=NOW(), lease=DATE_ADD(...), job_version=job_version+1 WHERE id=? AND job_version=<seq> AND status='RUNNING'`，成功则 `seq++`（与 DB 同拍）；② `finalizeJob`：**先做 job 门（版本+状态 CAS，0 行即停）再改 attempt**——job `SET status=终态, processed_rows=..., finished_at=NOW(), [SUCCESS: file_path/file_size/expires_at], heartbeat_at=NULL, lease=NULL, job_version=job_version+1 WHERE id=? AND job_version=<seq> AND status='RUNNING'`，成功后才 `UPDATE export_job_attempt SET status=同终态, finished_at=NOW(), error_message=... WHERE job_id=? AND status='RUNNING'`（归属已由 job 门证明，attempt 无需改 attempt_no 定位）。**任何守卫命中 0 行 = 该 job 已被他人接管**（租约回收置 FAILED / 过期置 EXPIRED / 重试-claim 已把版本推前）→ 抛专用 `StaleExecutionException` → `executeExport` 在 catch(Throwable) **之前**单独捕获 → `disposeQuietly` + **只删除本 attempt 自己的 tmp** + 记 warn + **静默返回（不落任何终态、不 deleteTaskDir、不 DLQ，消费者照常 ack）**。catch(Throwable)（真业务/IO/查询失败，DB 可达且仍属我们）保持现状：`dispose` → `deleteTaskDir` → `finalizeJob(FAILED)`。`finalizeJob` job 门 0 行时先 selectById 判定——`status != RUNNING` 或 `job_version` 已推进 → 归 Stale（静默）；否则才是真异常再抛（现状 `IllegalStateException` 兜底保留）。注意：**claim/retry/回收这类"非活跃 worker 的状态写入"用 `status` CAS 且同样 `job_version+1`**，不做版本 CAS（它们本就无权在该行 RUNNING 时写）。 |
| R5 | "表字段心跳时间"+"扫描 RUNNING" | `.tmp` 写盘路径若所有 attempt 共用 `export.xlsx.tmp`，stale worker 与新 attempt 会写同一文件（撕裂/误删） | **写盘 tmp 文件名带本次执行在 claim 时的版本号**：`ExportFileStore` 增 `attemptTmpFile(jobId, startSeq)` = `root/<jobId>/export.<startSeq>.tmp`（`startSeq`=execute 开始时 `job.jobVersion`，claim 每次 +1 保证跨执行唯一）。每个 worker 只写自己 startSeq 的 tmp、Stale 退出只删自己 startSeq 的 tmp（R4）→ 不同执行的文件写盘互不相交；`finalFile` 仍唯一 `export.xlsx`，只由 `publishAtomically(自己的 tmp→export.xlsx)` 产出（原子 move 覆盖）。**发布前再校验一次归属**：`publishAtomically` 前 selectById，`job_version` 已 ≠ `seq` 或非 RUNNING → 走 Stale 分支不发布。残余窗口（版本复核与 move 之间的微秒级竞争，stale 内容可能覆盖新文件但 DB 永不登记错 file_path/file_size，且 SUCCESS 的 file_size 以磁盘实读为准）→ 接受并文档化，不为它做 per-attempt 最终文件命名。 |
| R6 | 孤儿文件"已完成的场景：原子生成失败的 .tmp 删除、未登记数据库的 .xlsx 删除" | 是否要新增独立"孤儿清扫"扫描 | **不新增独立扫描**。三点已覆盖：① `.tmp 原子生成失败`→ 既有 `executeExport` catch 的 `deleteTaskDir` 与 Stale 分支删己 tmp（R4/R5）；② `未登记 .xlsx`（=已发布但 finalize 未落 SUCCESS 的 `root/<jobId>/export.xlsx`，job 停 RUNNING、`file_path` 仍 NULL）→ 租约回收(R3)把 job 置 FAILED 后 `deleteTaskDir` 整目录删掉；③ 真孤儿目录（job 行不存在）本系统不存在删除 job 的路径，不做兜底。 |

**裁决补充 R-F（前端对 job_version 的消费口径，纠正摘要"轮询拦截"字面）**：在 R0 的单调写序号语义下，正确消费规则是**"只接受严格更大的版本号"**——前端保存各任务已见最大 `jobVersion`，收到某任务的版本 ≤ 已见 → 判定为历史旧数据/重复事件，丢弃；> 已见才应用。该规则服务于**后续 SSE 的增量事件合并**（事件乱序/重放时按版本去旧）。**但本期不实现 SSE**：现有轮询是**整表快照替换**（`load` 每次 `setList(result.list)` + 请求取消防竞态，无乱序），且"版本相等 ⇒ 内容相同"（本 job 每次写入都 bump，同版本无写入），因此轮询无需按版本拦截——照旧整表替换即正确，硬加"只接受更大"反而会把未变化的等版本行（如静止的 SUCCESS/PENDING 短窗）丢弃造成闪烁。故本期前端动作 = **① `jobVersion` 透传进 `ExportJobVO`/`ExportCenterJob`；② 不在轮询里做版本 gate；③ 把"只接受严格更大版本"作为 phase13 SSE push 的合并契约写进 after-doc**。轮询谓词扩到 PENDING 是另一件事（R8），照做。

## 六、后端改动 C：executeExport —— 写序号守卫 + Stale 静默退出 + 每批心跳

`executeExport` 重构为：捕获 `startSeq` → 每批进度 UPDATE 带版本 CAS 并刷心跳 + bump → 发布前归属复核 → finalize 先 job 门再 attempt（SUCCESS 落 `expires_at`）。骨架（关键点标注，非逐行照抄）：

```java
public void executeExport(long jobId) {
    // 读 job（claim 已提交，能读到 claim 后 job_version = startSeq）。null → IllegalStateException 走异常路径
    ExportJob job = exportJobMapper.selectById(jobId);
    if (job == null) throw new IllegalStateException("导出任务不存在: jobId=" + jobId);
    long startSeq = job.getJobVersion();            // R5: 本执行 tmp 后缀（claim 每次+1 → 跨执行唯一）
    long seq = startSeq;                            // R4: 本地预期号，随每次成功写回 +1，与 DB 同拍

    Path tmp = store.attemptTmpFile(jobId, startSeq);
    Path out = store.finalFile(jobId);
    ExcelFileWriter writer = new ExcelFileWriter(tmp, sxssfRowWindow);
    long committed = 0L;
    try {
        // ...读 snapshot/columns 同现状...
        writer.open();
        writer.writeHeader(...);
        committed = writeBatches(writer, job, snapshot, cols);   // 见下：版本 CAS + 心跳，返回后 seq 已同步
        writer.close();
        // R5: 发布前归属复核 —— 已易主则不发布
        ExportJob fresh = exportJobMapper.selectById(jobId);
        if (!ExportJobStatus.RUNNING.name().equals(fresh.getStatus()) || fresh.getJobVersion() != seq) {
            throw new StaleExecutionException(jobId, seq);
        }
        publishAtomically(tmp, out);
        long size = Files.size(out);
        finalizeJob(jobId, SUCCESS, seq, committed, null, store.relativePath(jobId), size); // job 门→attempt
    } catch (StaleExecutionException e) {
        // R4: 已被他人接管(租约回收置FAILED/过期置EXPIRED/新claim已推进版本)——静默退出：不落终态/不deleteTaskDir/不进DLQ
        writer.disposeQuietly();
        store.deleteAttemptTmp(jobId, startSeq);    // 只删自己这次执行的tmp，绝不动同目录其它文件
        log.warn("导出执行已被接管(Stale), 静默退出: jobId={}, seq={}, reason={}", jobId, seq, e.getMessage());
    } catch (Throwable t) {
        // 真失败(本执行仍归属、DB可达)：保持现状 —— 清整目录再落 FAILED
        writer.disposeQuietly();
        store.deleteTaskDir(jobId);
        String reason = reasonOf(t);
        log.error("导出执行失败, 尝试落 FAILED 终态: jobId={}, reason={}", jobId, reason, t);
        finalizeJob(jobId, FAILED, seq, committed, reason, null, null);
    }
}
```

要点：
- **每批心跳 = 进度车上的便车 + bump 同一 UPDATE**（R0/R3 零额外写）。`writeBatches` 的进度 UPDATE 改为（把 `seq` 作引用或返回新值）：
  ```java
  int n = exportJobMapper.update(null, new LambdaUpdateWrapper<ExportJob>()
          .eq(ExportJob::getId, job.getId())
          .eq(ExportJob::getJobVersion, seq)                    // 守卫：0 行=已易主（R4）
          .eq(ExportJob::getStatus, ExportJobStatus.RUNNING.name())
          .setSql("processed_rows = processed_rows + " + size)
          .setSql("heartbeat_at = NOW(), lease = DATE_ADD(NOW(), INTERVAL " + leaseSeconds + " SECOND)")  // 心跳便车
          .setSql("job_version = job_version + 1"));            // 单调写序号
  if (n == 0) throw new StaleExecutionException(job.getId(), seq);
  seq++;                                                        // 本地与 DB 同拍（可用 int[] 或自定义返回值带出）
  ```
- `finalizeJob` 签名加 `long seq`；**顺序=先 job 门后 attempt**（R4）：
  - job 门：`UPDATE export_jobs SET status=终态, processed_rows=committed, finished_at=NOW(), [SUCCESS: file_path, file_size, setSql("expires_at = DATE_ADD(NOW(), INTERVAL "+expireSeconds+" SECOND)")], heartbeat_at=NULL, lease=NULL, job_version=job_version+1 WHERE id=? AND job_version=<seq> AND status='RUNNING'`；0 行 → selectById 判定：`status != RUNNING` 或 `job_version` 已推进 → 抛 `StaleExecutionException`；否则维持 `IllegalStateException`。
  - attempt（job 门成功后）：`UPDATE export_job_attempt SET status=同终态, finished_at=NOW(), error_message=... WHERE job_id=? AND status='RUNNING'`（归属已由 job 门证明；0 行属数据异常→抛 `IllegalStateException`）。
  - `expireSeconds` 由构造注入 `@Value("${export.expire-hours:24}") int expireHours`（类内 ×3600），与 `leaseSeconds` 同批注入；两处 UPDATE 仍在同一 `TransactionTemplate` 内（勿改注解自调用）。
- `publishAtomically` / `ExcelFileWriter` / `reasonOf` 不动；`StaleExecutionException` = 私有静态类（`RuntimeException` 子类，携带 jobId/seq），仅本类内部使用。
- 消费者 `ExportJobConsumer` **零改动**：Stale 静默返回 → `executeExport` 正常返回 → 照常 ack（本消息对应的执行已结束，job 归他人所有是既定事实，ack 无害）。

```java
@Override
@Transactional
public ExportJobVO retry(long jobId) {
    // 1. 存在性与状态：仅 FAILED；其余/不存在一律真实 4xx envelope
    ExportJob job = exportJobMapper.selectById(jobId);
    if (job == null) throw new BizException(404, "导出任务不存在");
    if (!ExportJobStatus.FAILED.name().equals(job.getStatus())) {
        throw new BizException(409, "仅失败状态的任务可重试");
    }
    // 2. job FAILED→PENDING + 进度归零 + 版本+1（R0/R1）；WHERE status=FAILED 作 CAS：并发双击第二次 0 行 → 409
    int jobUpdated = exportJobMapper.update(null, new LambdaUpdateWrapper<ExportJob>()
            .eq(ExportJob::getId, jobId)
            .eq(ExportJob::getStatus, ExportJobStatus.FAILED.name())
            .set(ExportJob::getStatus, ExportJobStatus.PENDING.name())
            .set(ExportJob::getProcessedRows, 0L)
            .setSql("job_version = job_version + 1"));
    if (jobUpdated == 0) throw new BizException(409, "仅失败状态的任务可重试");
    // 3. 同一 outbox 行重投：published_at 置 NULL（dispatcher 5s 内拾取 → claim → 新 attempt）
    outboxEventMapper.update(null, new LambdaUpdateWrapper<OutboxEvent>()
            .eq(OutboxEvent::getJobId, jobId)
            .isNotNull(OutboxEvent::getPublishedAt)     // 已 NULL(理论不可达)则不动
            .set(OutboxEvent::getPublishedAt, null));
    // 4. 旧 FAILED attempt 行原样归档，任何代码不UPDATE终态attempt；新 attempt 由重投被 claim 时落账(attempt_no+1)
    return toVO(exportJobMapper.selectById(jobId));
}
```

要点：
- **不重投"新消息体同步发送"**：置 NULL 后靠 dispatcher（≤5s）重投，与正常新建同一条入队路径（R1）。想即时可用后续再议，本期不加第二条投递路径。
- 原消息此刻已 ack（FAILED 是消费者正常终态 ack），无重投死循环。
- retry 的版本 +1 让 FAILED(旧 N) 之后的 PENDING(N+1) 成为"更大版本"新快照；claim 再 +1 → RUNNING(N+2)，全程单调，前端按"只接受更大"可识别重试后的新执行（R0/R-F）。

## 九、后端改动 F：扫描器 ExportRecoveryScanner（R3/R7，新组件）

`backend/.../export/recovery/ExportRecoveryScanner.java`（`@Component`；租约回收与过期回收两个 `@Scheduled` 方法，内部各循环小批量处理，避免长事务）：

- **租约回收** `@Scheduled(fixedDelay = 60_000, initialDelay = 30_000)`：
  ```
  循环: 查 export_jobs WHERE status='RUNNING' AND (lease IS NULL OR lease < NOW()) ORDER BY id LIMIT 50
    ├─ 空 → break
    ├─ 每行同一事务(TransactionTemplate)：
    │     UPDATE export_job_attempt SET status='FAILED', finished_at=NOW(),
    │           error_message='执行租约过期(心跳停止),由扫描回收' WHERE job_id=? AND status='RUNNING'
    │     UPDATE export_jobs SET status='FAILED', heartbeat_at=NULL, lease=NULL, job_version=job_version+1
    │           WHERE id=? AND status='RUNNING'                     -- status CAS 防与真实终态/并发竞争
    ├─ 事务落定后 store.deleteTaskDir(jobId)   // 删遗留 .tmp / 已发布未回写 .xlsx
    └─ 单行异常吞掉记 warn，继续下一行
  ```
  每行事务独立、失败不影响其它；两处 UPDATE 同事务原子（与 finalizeJob 同款手法）。**只置 FAILED、不重投 outbox**；版本 +1 让 FAILED 快照成为"更新版本"供读者识别（R0/R3）。
- **过期回收** `@Scheduled(fixedDelay = 3_600_000, initialDelay = 60_000)`：
  ```
  循环: 查 export_jobs WHERE status='SUCCESS' AND expires_at IS NOT NULL AND expires_at <= NOW() ORDER BY expires_at LIMIT 50
    ├─ 空 → break
    ├─ 每行：先 store.deleteTaskDir(jobId)    // 先删文件（照摘要顺序）
    ├─ 再 UPDATE export_jobs SET status='EXPIRED', job_version=job_version+1 WHERE id=? AND status='SUCCESS' AND expires_at=该行expires_at  -- CAS防并发/边界竞争
    └─ 单行异常吞掉记 warn 继续
  ```
  依赖 V7 的 `idx_status_expires`。attempt 表不落 EXPIRED（SUCCESS attempt 是执行历史，保留；EXPIRED 是 job 级生命周期状态）。

`application.yml` 增：`spring.task.scheduling.pool.size: 4`（R7）、`export.lease-seconds: 300`、`export.expire-hours: 24`。

## 十二、验收清单

**后端（docker 全栈起后，造任务打 curl）**：
- **迁移**：`SHOW COLUMNS FROM export_jobs` 见 job_version/heartbeat_at/lease/expires_at；回填——把一个已 SUCCESS 任务 `expires_at` 应为 finished+24h。
- **job_version 单调推进**：新建任务 `job_version` 初始 0；claim 转 RUNNING 后 =1；每批进度后递增（可在导出中查 DB：`job_version` 与 `processed_rows` 同步上涨、恒比上一读大）；终态再 +1。下载/列表 VO 带正确 jobVersion。
- **正常链路回归**：新建 → SUCCESS → 下载 200 正常；SUCCESS 后 `heartbeat_at/lease` 为 NULL、`expires_at`=finished+24h。
- **重试**：
  - 手工把一任务置 `FAILED`（或等一次真实失败）→ `POST /api/export-job/<id>/retry` → 200，VO `status=PENDING, processedRows=0, jobVersion` 比 FAILED 时大 1；≤5s 内被 claim 转 RUNNING（jobVersion 再 +1）、attempt 表新增 attempt_no=2 行、outbox `attempt_count=2`；旧 attempt#1 仍 FAILED 原样。
  - 对 SUCCESS/RUNNING/PENDING/EXPIRED 任务 retry → 409"仅失败状态…"；不存在 id → 404；并发双击（几乎同时两次）→ 一次 200 一次 409。
  - **旧 attempt 归档断言**：retry 前记录 attempt#1 的 status/finished_at/error_message，retry+完成后该行字段零变化。
- **防倒退（Stale 守卫，DB 层面打）**：把一 RUNNING 大任务制造两次执行——模拟 stale 场景：先 `UPDATE export_jobs SET lease=NULL` 触发租约回收置 FAILED（job_version 已被回收推进），再 retry 出新 RUNNING(claim 再 +1)；随后**手工按旧 job_version 对 job 执行进度 UPDATE**（`SET processed_rows=processed_rows+999 WHERE id=? AND job_version=<旧值> AND status='RUNNING'`）→ 断言影响 0 行；真代码路径里 stale worker 的写回抛 Stale 后**不落 FAILED、不 deleteTaskDir**（可加日志断言：任务目录仍在、job 仍是新执行的 RUNNING/SUCCESS）。
- **租约回收**：把一 RUNNING 任务 `UPDATE export_jobs SET lease=NULL`（或 DATE_SUB 过期）→ ≤1min 后该任务 job/attempt 同事务置 FAILED（attempt error_message="执行租约过期…"）、任务目录被删；outbox 不重投（published_at 维持原值、无新 attempt）。
- **过期回收**：把一 SUCCESS 任务 `UPDATE export_jobs SET expires_at = NOW() - INTERVAL 1 SECOND` → ≤1h（可临时把扫描 fixedDelay 调小验证，如临时 10s）后：目录删除、`status=EXPIRED`（job_version+1）；再下载 → 404"已过期清理"；再 retry → 409。
- **门禁**：`./mvnw` 编译+单测全绿；应用可起、`/actuator/health` rabbit UP；调度三个任务无异常日志。

**前端**：
- 导出中心：SUCCESS 行"下载文件"、FAILED 行"重试"、其余行为空；EXPIRED 行状态列"已过期"、无按钮。
- 点重试成功 → 行消失/置 PENDING（load 刷新）；双击第二次 toast 409 原文；轮询在 PENDING/RUNNING 期间持续刷新到 SUCCESS/消失；列表行带 jobVersion（console/网络可验）但不因版本变化异常闪动（静止行稳定显示）。

## 十三、已拍板的解读（可在实施前推翻）

1. **job_version = export_jobs 的单调写序号**（只增不减，本 job 全生命周期）：凡是把 job 往前推进的状态/进度写入都 +1——claim、每批进度、finalize 终态、重试、租约回收、过期回收。双重角色：活跃 worker 写回的乐观 CAS（防 stale 倒退）+ 读者/将来 SSE 的快照事件序号。**只加在 jobs 表**；attempt 表用既有 attempt_no 表达每执行计数（R0）。摘要"每次任务开始执行时从 1 计算"不适用于 job_version（跨重试会重复版本号、破坏单调），attempt_no 已表达该语义。
2. **重试**：仅 FAILED；`POST retry` 同事务 `FAILED→PENDING + processed_rows=0 + job_version+1 + 同 outbox 行 published_at→NULL`，靠 dispatcher ≤5s 重投开新 attempt（claim 再 +1）；旧 FAILED attempt 永不 UPDATE（R1）。
3. **守卫矩阵**：活跃 worker 维护本地预期号 `seq`（初值=claim 后 job_version）：每批进度/终态写回一律 `WHERE id=? AND job_version=<seq> AND status='RUNNING'` 并 `job_version+1`，成功后 `seq++`；finalize **先 job 门成功再改 attempt**；0 行=已易主 → `StaleExecutionException` → dispose + 只删己 startSeq tmp + 静默返回，不落终态/不 deleteTaskDir/不 DLQ。claim/retry/双回收用 status CAS 并同样 bump（R4）。
4. **tmp 名带 claim 版本号**（`export.<startSeq>.tmp`）+ 发布前归属复核；per-attempt 最终文件命名不做，残余微秒窗口接受并文档化（R5）。
5. **孤儿清扫不新增扫描**：catch `deleteTaskDir` + Stale 删己 tmp + 租约回收 `deleteTaskDir` 三点覆盖 12.0 第 4 步全部（R6）。
6. **EXPIRED/expires_at**：SUCCESS 落终态写 expires_at=finished+24h；每小时扫描先删文件再置 EXPIRED（bump）；下载对 EXPIRED → 404"已过期清理"；EXPIRED 不可下载/重试（R2/R8）。
7. **心跳/租约两列写 jobs，随每批进度 UPDATE 顺带刷新（零额外写），claim 重置**；租约回收 60s 扫 `RUNNING AND (lease IS NULL OR lease<now)` → 两表同事务置 FAILED（attempt 带 error_message）→ 删目录，只置 FAILED 不自动重投（R3/R7）。
8. **调度池**：`spring.task.scheduling.pool.size:4`，租约/过期两扫描放 `ExportRecoveryScanner`（R7）。
9. **前端**：状态/常量加 EXPIRED、不加 tab；轮询谓词扩到 PENDING；FAILED 行出"重试"；**`columns` 随重试迁入组件（`useMemo [load]`）**，因重试须触发列表刷新；**jobVersion 本期只透传、轮询不做版本 gate**（整表快照替换无乱序且"版本相等⇒内容相同"），"只接受严格更大版本"作为 phase13 SSE 合并契约落档（R-F）——纠正摘要"轮询按版本拦截"字面。
