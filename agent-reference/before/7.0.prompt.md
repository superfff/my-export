# 阶段 7.0 完整实施提示语

> 来源：`agent-reference/before/7.0.md`
> 用途：可直接投喂给后续编码会话，指导其实现"后端包结构重组（工程重构）→ 导出中心只读列表（前端页面 + 后端查询接口）+ 订单模块两处界面缺陷修复"。
> 性质：仅实施蓝图，本文档不含代码，也不对任何代码做过编辑。
> 约定沿革：上一阶段为 `6.0`（已打通"前端异步导出任务发起 → 后端校验 → `export_jobs` 入库"，任务恒 `PENDING`，无任何推进路径）。阶段 `8.0` 之后才会引入真正执行导出 / 推进状态 / 产出文件的能力。

## 一、背景与目标

全栈订单导出项目：`frontend/`（React18 + Vite + TS + AntD5 + pnpm）+ `backend/`（SpringBoot3 + Java21 + MyBatis-Plus + Flyway，端口 8080）+ MySQL（`order_db`）。信封统一 `ApiResponse{code,message,data,traceId}`，`code=0` 成功；列表错误沿用 `IllegalArgumentException → HTTP 200 + code=400`；`TraceIdFilter` 注入 `traceId`。

**当前后端结构（问题点）**：所有 Java 类都平铺在 `com.example.order.*` 下——`common/config/enums` 塞在订单包内，`ExportJob*` 与 `Order*` 在每个 MVC 层（controller/service/mapper/entity/dto）**混在一起**，启动类 `OrderApplication` 也在 `com.example.order` 根上。Mapper 各自带 `@Mapper`（无 `@MapperScan`），启动类默认只扫 `com.example.order.*`。

当前业务进度（可直接读到代码确认）：

- 订单页 `/order`：标题行 + 筛选表单（`OrderQueryForm`：六键筛选 + `sortField/sortOrder` 两个 Select，目前**无默认值且 allowClear**）+ `PageTable`（表格区内部滚动、底部分页，表格高度用 `ResizeObserver` 量 `.tableWrap` 整高作为 `Table.scroll.y`）+ 导出按钮 + `ExportModal`。
- 后端：`GET /api/order` 分页查询（未显式传排序时默认 `created_at DESC`，并恒追加 `id ASC` 第二排序键做稳定分页）；`POST /api/export-job` 创建导出任务（6.0 已打通，返回 `ExportJobVO`）。
- `export_jobs` 表字段（`V2`，唯一版本线到 V2，无其他迁移）：`id / idempotency_key / request_hash / export_mode / status / filename / export_columns / scope_snapshot / expected_total / max_order_id / created_at / updated_at`。任务状态机枚举 `PENDING/RUNNING/SUCCESS/FAILED`，当前表中所有行都只会是 `PENDING`。
- 前端类型：`types/order.ts` 已有 `ExportJobStatus`、`ExportJobVO`（含 `maxOrderId`）、`ExportMode` 等。

**本阶段目标**：

1. **后端包结构重组**（第二节，工程重构、行为不变）：把揉在订单域里的导出任务逻辑**剥离成平级模块** `com.example.export`；跨模块可复用的件收进平级 `com.example.common`；基础设施 `config` 独立成平级包；`order` 模块就地保留原 MVC 子包。重构完成后，导出中心相关代码一律落在 `export` 模块内。
2. **修复订单管理模块两处界面缺陷**（第三节）。
3. **新增"导出中心"只读列表**（第四、五节）：后端在 `export` 模块内复用 `/api/export-job` 以 RESTful 形式新增**列表查询接口**，数据来自 `export_jobs`，默认按创建时间降序；前端新增页面（顶部标题"导出中心" + 同行右侧状态 tab + 表格区滚动 + 底部分页，无任何行内按钮操作）。

**明确本期不做（防止实现越界）**：

- 导出中心**不做任何按钮操作**（下载 / 重试 / 删除 / 查看详情均不做）——需求原文"暂不提供按钮操作"。
- **不推进任务状态**：没有任何代码把任务从 `PENDING` 推进到 `RUNNING/SUCCESS/FAILED`。状态 tab 与状态列只是"可筛 / 可展示"的枚举结构；当前 `SUCCESS/RUNNING/FAILED` 筛选命中空集是**合法结果**，不是 bug。
- **不改 `export_jobs` 表结构、不加 Flyway 迁移**：导出实际条数 / 进度 / 完成时间 / 文件大小四列本期**没有数据源**（真正导出在后续阶段才会产出），只在表头占位、无数据渲染 `-`。绝不为此先建空列（见第八节拍板）。
- 结构重组**不改任何行为**：接口路径 / HTTP 语义 / 报文字段 / 表名 / 表结构 / 错误文案一律不变；**不把 `Order*` 类搬出订单模块**；**不改前端**（后端纯包级移动，前端无需感知）。绝不借机重命名 DTO 字段、改动 409 文案或任何既有契约。
- **不引入新技术 / 新依赖**；不改动 `POST /api/export-job` 创建链路与两条 409 文案常量。
- 后端不改订单列表查询逻辑本身（A2 的"后端兜底默认排序"已具备，只做回归验证）。
- 导出中心**不做行选择**（只读），复用 `PageTable` 的"无选择分支"。

### 异常更名（ExportBizException → BizException）

`ExportBizException` 只携带 `int httpStatus` + 文案，本质是**通用业务异常**，并非 export 专属。因共享的 `GlobalExceptionHandler` 必须引用它，若放 export 会造成 `common → export` 反向依赖，故：

- `common/ExportBizException.java` → `common/BizException.java`（`package com.example.common`，类名 `BizException`，字段/构造语义不变）。
- `GlobalExceptionHandler`（com.example.common）的 handler 签名同步为 `@ExceptionHandler(BizException.class)`（方法可改名 `handleBiz`），逻辑不变。
- `ExportJobServiceImpl`（com.example.export.service.impl）所有 `throw new ExportBizException(400/409, …)` 改 `new BizException(…)，import com.example.common.BizException`。

### 模块间依赖说明（保留，不强拆）

- `export` 模块在创建任务时读取订单统计（`OrderMapper.selectExportScopeStats` 对 `t_order` 只读 `count(*)/max(id)`），保留 **export → order 的单向模块依赖**（复用同一套谓词拼装，不复刻 SQL，不在 export 另建读表 Mapper）。
- `common` 只放跨模块可复用件，**不得**引用 `order/export` 业务类；`config` 是纯基础设施。
- Mapper 沿用各自 `@Mapper` 注解（无需 `@MapperScan`）；启动类默认扫描根包 `com.example`。

### 重构完成判据

- `mvnw` 编译通过；启动应用后以下行为与重构前**完全一致**：`POST /api/export-job`（创建 + 幂等 409/400）、`GET /api/order`（含排序默认降序）、健康检查；envelope/traceId 不变。
- 前端无需任何改动即可正常联调。

## 三、修复 A：订单管理模块两处缺陷

### A1 表格区域分页器遮挡末行（最后一行的数据被吞掉一截）

- **症状**：订单管理表格数据较多时，末行下半部分被裁掉，看起来像被底部分页条挡住；页面本身不滚动。
- **根因方向**（已从 `PageTable/index.tsx` 与 `PageTable.module.css` 确认）：`PageTable` 把 `.tableWrap`（`flex:1; min-height:0; overflow:hidden`）的**整高**经 `ResizeObserver` 量出后直接赋给 antd `Table` 的 `scroll.y`。而 antd 固定表头布局是"`.ant-table-header` 表头高度 + 内容区高度 `y`"叠加渲染，导致内容总高比容器多出一个表头高度，`.tableWrap` 底部溢出裁切 → 末行被吞。
- **修复要求**：让"滚动内容区（body）的实际可视高度"＝容器可用高度 **减去固定表头高度**（实现上可测量 `.ant-table-header` 的实测高度后回填 `scroll.y`，或改为给不含表头的滚动容器定高）。修复必须落在共享的 `PageTable` 组件内（含"无选择分支"与"带选择分支"两条路径），使订单页与新建的导出中心**同时**受益。
- **不得引入新依赖**（不引 react-virtualized / 不引第三方高度库）。
- **验收（需本地起前端 + 后端肉眼确认，并用窗口缩放 / 换页 / 多数据量复验）**：
  1. 表内数据超高时，仅表格 body 在自身区域滚动，末行**完整可见**，不被分页条遮挡；
  2. 底部分页条固定、不随内容滚动；整页（含内容区）不出现纵向滚动条；
  3. 空数据、仅有表头、数据不足一屏、切换每页条数等情形均不出现错位/遮挡；
  4. `selectionNotice`（勾选提示条）出现/消失引起高度变化时，表格高度能跟随自适应（`ResizeObserver` 仍生效），不回归。

### A2 筛选表单排序默认值 + 不可清空 + 后端兜底

- **前端**：`frontend/src/pages/order/OrderQueryForm.tsx`
  - 排序字段 Select **默认选中 `创建时间`（值 `createdAt`）**；排序方向 Select **默认选中 `降序`（值 `desc`）**（用 `Form` 的 `initialValues` / `Form.Item initialValue` 实现）。
  - 移除这两个 Select 的 `allowClear`（**不可清空**，只能在两个取值间切换）。
  - "重置"后回到以上默认值，不允许出现"空排序"态。
- **页面状态对齐**：`frontend/src/pages/order/index.tsx` 让查询状态与表单默认一致——定义 `DEFAULT_SORT = { sortField: 'createdAt', sortOrder: 'desc' }`；`query` 的初始 `useState` 与 `handleReset` 都落到 `DEFAULT_SORT`，保证**从首次加载起每次请求都显式携带** `sortField=createdAt&sortOrder=desc`（后端本就按白名单动态排序，等价于默认降序，见下）。
- **后端兜底（不改代码，仅回归验证）**：`OrderServiceImpl.page`（com.example.order.service.impl）在请求**未显式传** `sortField/sortOrder` 时，仍默认 `ORDER BY created_at DESC`（并保留 `id` 第二排序键防分页漂移）。这是"走接口但不传参"时的兜底，与前端默认值等价。
- **验收**：
  1. 打开订单页，两个下拉即显示"创建时间 / 降序"，且无清除（清空）入口；
  2. 点"查询"网络请求携带 `sortField=createdAt&sortOrder=desc`；"重置"后仍恢复为该默认并重新查询；
  3. 直接调 `GET /api/order`（不带 `sort*`）返回的首行 `createdAt` 是最大值（降序兜底成立）；
  4. 用户切到"金额 / 升序"等其它选项时按所选生效，切回即回默认。

## 四、后端：导出中心列表接口（落于 export 模块）

**复用 `POST /api/export-job` 所在资源，RESTful 增补 GET（同一 `com.example.export.controller.ExportJobController`、同 `/api/export-job` 前缀），严格 MVC 分层。**

### 端点与参数

```
GET /api/export-job?status=PENDING&page=1&pageSize=20
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `status` | string | 否 | 任务状态筛选，取值 `PENDING / RUNNING / SUCCESS / FAILED`。**不传 = 全部**（即"全部"tab）；trim 后为空串等价于不传。非法值 → 校验错误（见下）。 |
| `page` | long | 否 | 页码从 1 起，缺省/非法(<1) → 1（对齐订单页语义）。 |
| `pageSize` | long | 否 | 每页条数，缺省/非法(<1) → 20。 |

- 无需 `Idempotency-Key`，纯只读列表。
- **排序**：固定 `ORDER BY created_at DESC, id DESC`（默认创建时间降序；追加 `id DESC` 第二键——同刻创建的任务按较新的 id 排前，分页稳定）。列表接口**不支持** `sortField/sortOrder` 参数，请勿在导出中心加排序 UI。

### 响应

HTTP 200 + 信封 `PageResult`：

```jsonc
{ "code": 0, "message": "ok",
  "data": { "list": [
    { "id": 12, "filename": "订单导出_20260903", "exportMode": "FILTERED",
      "status": "PENDING", "expectedTotal": 1234, "maxOrderId": 98765,
      "createdAt": "2026-09-03T10:00:00" }
    // ... 注意：不含 idempotencyKey / requestHash / scopeSnapshot / exportColumns 等内部列
  ], "total": 3, "page": 1, "pageSize": 20 },
  "traceId": "..." }
```

- **行对象直接复用现有 `ExportJobVO`**（`com.example.export.dto.ExportJobVO`：`id / filename / exportMode / status / expectedTotal / maxOrderId / createdAt`），不新增第二套"创建/列表"VO，避免口径漂移。`ExportJobVO` 的 javadoc 由"创建成功返回"改为"创建与列表查询共用"。
- 实际条数 / 进度 / 完成时间 / 文件大小**后端本期不返回**（无数据源、不入 VO），由前端表头占位渲染 `-`。
- **错误语义**：`status` 非法 → 抛 `IllegalArgumentException`，由 `com.example.common.GlobalExceptionHandler` 按 `HTTP 200 + code=400` + envelope 返回（**与 `GET /api/order` 排序白名单报错同款语义，勿用 `BizException`/真 409**）。文案示例：`不支持的状态筛选：FOO，仅支持：PENDING、RUNNING、SUCCESS、FAILED`。

### 后端改动清单（在 export 模块内新增/修改）

- `export/controller/ExportJobController.java`：新增 `@GetMapping` 方法 `list(ExportJobQueryDTO query)`，返回 `ApiResponse<PageResult<ExportJobVO>>`；方法/类 javadoc 注明"创建 + 列表共用同一资源"。
- `export/dto/ExportJobQueryDTO.java`（新增）：`record ExportJobQueryDTO(String status, Long page, Long pageSize)`，字段含义见上表。
- `export/service/ExportJobService.java` + `export/service/impl/ExportJobServiceImpl.java`：新增 `PageResult<ExportJobVO> page(ExportJobQueryDTO query)`。实现：
  1. `status` trim 后非空时校验 ∈ 四枚举；非法抛 `IllegalArgumentException`（文案见上）。
  2. 归一化 `page/pageSize`（缺省/非法 → 1 / 20）。
  3. `LambdaQueryWrapper<ExportJob>`：命中时 `eq(ExportJob::getStatus, 规范化大写状态串)`；`orderByDesc(createdAt)` + `orderByDesc(id)`。
  4. `selectPage(new Page<>(pageNum,pageSize), wrapper)` → 每条映射 `ExportJobVO`。
  5. 建议在 Impl 内抽私有 `toVO(ExportJob)`，让 `create()` 结尾与列表共用同一套映射（避免两处拼 VO 漂移）；`create()` 行为不变。
- 不改：`V2` 迁移、`ExportJob` 实体、`ExportJobStatus/ExportMode` 枚举、创建接口契约。

**curl 验证矩阵**（`status` 过滤、排序、分页、非法值；路径与报文与结构重组前后均不变）：

```bash

curl 'http://localhost:8080/actuator/health'
```

- "导出范围"即所选模式的描述；"进度"列的展示口径收敛到页面内一个**纯函数**便于测试：
  ```ts
  /** 进度 0-100：优先用后端返回 progress；否则按 actualTotal/expectedTotal 推导；都缺省返回 null → 显示 '-' */
  function resolveExportProgress(job: ExportCenterJob): number | null {
    if (job.progress != null) return Math.min(100, Math.max(0, Math.round(job.progress)));
    if (job.actualTotal != null && job.expectedTotal > 0) {
      return Math.min(100, Math.max(0, Math.round((job.actualTotal / job.expectedTotal) * 100)));
    }
    return null;
  }
  ```
- `formatDateTime`（`utils/format.ts`）对空值已返回 `'-'`，完成时间可直接复用。
