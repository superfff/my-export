## 一、背景与目标

全栈订单导出项目：`frontend/`（React18 + Vite + TS + AntD5 + pnpm）+ `backend/`（SpringBoot3 + Java21 + MyBatis-Plus + Flyway + RabbitMQ，端口 8080）+ MySQL（`order_db`）+ RabbitMQ。信封统一 `ApiResponse{code,message,data,traceId}`；`TraceIdFilter` 以 MDC 键 `traceId`、HTTP 头 `x-trace-id` 贯穿。

**当前后端结构（可直接读到代码确认，均为 9.0 落地产物）**：

- `export` 模块 MVC：`controller/ExportJobController`、`service(+impl)/ExportJobService`、`mapper/*`、`entity/ExportJob、ExportJobAttempt、OutboxEvent`、`dto/ExportCreateRequest、ExportJobQueryDTO、ExportJobVO`、`enums/ExportJobStatus、ExportMode`、`outbox/OutboxDispatcher`、`mq/RabbitNames、RabbitTopologyConfig、ExportEventMessage、ExportJobConsumer`、`config/RabbitConfig`、`support/OrderExportColumns`（列白名单唯一来源）。
- 表结构（唯一版本线到 V5）：
  - `export_jobs`（V2+V5）：`id / idempotency_key(uk) / request_hash / export_mode / status(PENDING/RUNNING/SUCCESS/FAILED) / filename / export_columns(JSON 数组, 保序) / scope_snapshot(JSON) / expected_total / max_order_id / processed_rows / created_at / updated_at`。乐观锁用"状态即版本"（`WHERE id=? AND status=?`）。
  - `outbox_events`（V3+V4）：`id / job_id(uk,1任务=1事件) / trace_id / published_at / attempt_count / created_at / updated_at`；**未发布 ⟺ `published_at IS NULL`**（dispatcher 扫描与防重回写条件）。
  - `export_job_attempt`（V3）：`id / event_id / job_id / attempt_no(uk job_id+attempt_no) / status(RUNNING/SUCCESS/FAILED) / started_at / finished_at / error_message / created_at`；`finished_at / error_message` 在终态回写时已回填。
  - `t_order`（V1，只读）：`id / order_no / customer_name / phone / status(TINYINT 1/2/3) / amount DECIMAL(12,2) / created_at / updated_at / remark`。
- 行为现状：
  - `ExportJobServiceImpl.executeExport(jobId)`（不开长事务）：`writer = new ExcelFileWriter(Paths.get(fileDir, "export_"+jobId+".xlsx"), sxssfRowWindow)` → `open()`（建父目录）→ 解析 `scope_snapshot`（`ExportScopeSnapshot` record）与 `export_columns`（`readColumns`，**含白名单外字段直接抛 `IllegalStateException("export_columns 含白名单外字段: ...")` → FAILED，已实现**）→ `writeBatches`（keyset `id>lastId AND id<=max_order_id ORDER BY id LIMIT batchSize`，每批成功短事务 `processed_rows += 批行数`）→ `writer.close()`（flush 落盘）→ `finalizeJob(SUCCESS, committed, null)`；catch → `disposeQuietly` + `deleteFileQuietly(最终文件)` + `finalizeJob(FAILED, committed, reason)`。
  - `ExcelFileWriter`（`ExportJobServiceImpl` 内私有静态类）：`new SXSSFWorkbook(rowWindow)` + `compressTempFiles(true)` + 单 sheet `"订单"`；`writeRow` 对 `Number` 走 numeric 单元格、其余走 `setCellValue((String)value)`；`close()` = `Files.newOutputStream(file)` 包 `workbook.write`，`finally disposeQuietly`。
  - `OrderExportColumns`（枚举=白名单唯一来源）：`orderNo/customerName/phone` 走 `sanitize`；`amount` 返回 `BigDecimal.doubleValue()`（**numeric 单元格**）；`status` 1→未支付 2→已支付 3→已取消；`createdAt` 返回 `yyyy-MM-dd HH:mm:ss` 文本；`sanitize` 剔除控制/非法 XML 码点（→空格）并对首字符 `= + - @` 前置单引号；`byKey` 供 create 校验与 execute 反序列化共用。
  - `finalizeJob`：注入的 `TransactionTemplate` 同一事务 UPDATE attempt（置终态 + `finished_at` + 失败 `error_message`）与 job（置终态 + `processed_rows`；**9.0 不写 job 级 `finished_at`，本期 V6 起补写，见第六节**），两条均 `WHERE ... AND status='RUNNING'`，影响行数 0 抛错。**勿改回 `@Transactional` 自调用（同类自调用代理不生效）。**
  - `ExportJobConsumer`：解析+`claim` 包 `RetryTemplate(5 次)`；`claim=true` 则**循环外** `executeExport`，返回后 `basicAck`；`claim=false` 也 ack；仅解析失败/claim 重试耗尽或 `executeExport` 连终态都落不了而抛出才 `basicNack(requeue=false)` → DLX。`prefetch=1, concurrency=2`。
  - `application.yml`：`export.batch-size: 1000`、`export.sxssf-row-window: 100`、`export.file-dir: ${EXPORT_FILE_DIR:./data/export}`（配置化 root，已满足"root 由配置文件管理"）。
  - 部署：docker-compose backend 注入 `EXPORT_FILE_DIR: /app/data/export` + 命名卷 `export-files`；根 `.gitignore` 已含 `backend/data/`。
  - 后端测试：`OrderExportColumnsTest`（`sanitize`/`byKey` 共 4 例）已存在；前端有 vitest。
- 前端：本期**不改前端代码**，但导出中心「完成时间」列（`export-center/index.tsx` `dataIndex: 'finishedAt'`，类型 `ExportCenterJob.finishedAt?`）本就读 `job.finishedAt`——后端一直没返回该字段，故恒为 `'-'`；本期补 DB 列 + 终态回写 + `ExportJobVO` 返回后，该列随任务完成自动点亮。

**本阶段目标**：

1. **单元格文本格式优化**：金额列 `amount` 由 numeric 改为**文本单元格**，值统一保留小数点后 2 位（整数 `12` → `"12.00"`，DECIMAL 存值 `12.50` → `"12.50"`）；时间列已是格式化文本（`yyyy-MM-dd HH:mm:ss`），保持并补验收。
2. **白名单执行期兜底**：凡写入文件的列必须 ∈ 可导出白名单；"特殊渠道"（绕过创建接口校验、直接写 `export_jobs`）写入含白名单外字段的任务，在消费执行期**自动置 FAILED**（现状 `readColumns` 已抛错→FAILED，本期以直插 SQL 的 e2e 锁死该行为，创建接口 400 校验不变）。
3. **受控路径 + 任务隔离**：文件 root 由 `export.file-dir` 配置管理；所有写盘 / 清理 /（将来）下载统一经一个受控封装做"归一化 + 越界校验"，杜绝路径指向受控文件夹之外；文件按任务**独立子目录** `root/<jobId>/` 存放互不打扰。
4. **原子发布流转**：SXSSF 先写内部 `.tmp` 临时文件；workbook 全部写完并 `close` 后，用 Java NIO `Files.move(..., ATOMIC_MOVE)` **原子发布**对外 `.xlsx`（`.tmp` 与 `.xlsx` 同目录同卷，保证原子改名前提）；发布成功则删 `.tmp`（move 即消费掉）并回写 job/attempt 任务字段（状态、文件相对路径、文件大小、完成时间）；任一失败分支收敛回 9.0 的 catch/finalize 结构（详见第六节时序）。

**明确本期不做（防止越界）**：

- **不提供下载 / 不做文件对外提供**：`ExportFileStore.resolve(相对路径)` 只为下载留好受控入口并文档化，本期不实现下载接口；`export_jobs.filename` 仍只作展示。
- **前端零代码改动，但导出中心「完成时间」列随本期点亮**：后端补 `export_jobs.finished_at`（V6）+ 终态回写 + `ExportJobVO`/`toVO` 返回后，前端既有 `dataIndex: 'finishedAt'` 即有值；`fileSize` 仍为预留、本期不返回。
- **不把列白名单改成数据库表**：可导列集合 = `t_order` 静态 schema 的可导列，`OrderExportColumns` 枚举仍是唯一来源（YAGNI：列不会运行时变化）。
- **不改 9.0 关键机制**：幂等 409 / outbox 同生同灭与 `published_at IS NULL` 判据 / claim CAS 抢占 / keyset 水位 / 进度短事务 / ack 语义 / 四表职责 / "卡死 RUNNING 不自动恢复"边界——全部不动，只在其上叠本期四目标。
- **不做历史遗留文件的迁移/清扫**：9.0 生成的 flat `root/export_<id>.xlsx` 留在原地不去动；新产出走新布局。

**商讨考虑部分的裁决（10.0.md 第十八~十九行，需求方已确认口径）**：

1. **excel 存在 `/backend` 内（已 .gitignore） vs 系统临时文件夹，哪个更好** → 保留现状：**持久、配置化的 root（`export.file-dir`）**。理由：
   - 系统 `java.io.tmpdir` 是**易失**的：容器重建/重启即清、不随命名卷持久化，而生成文件后续要"下载/清理/供人取用"，必须能存活并有稳定底座；本地 `/backend` 只是开发期落点，已 `.gitignore` 防误提交，生产形态由 docker `EXPORT_FILE_DIR=/app/data/export` + 命名卷 `export-files` 承接（容器重建文件仍在）。
   - 受控路径需要一个**稳定不变的 root** 来做"归一化 + startsWith"校验；系统临时目录语义（`/tmp`、可被 OS 清理、多实例共享命名易撞）做 root 既不可靠也不利于隔离。
   - SXSSF 自己的行窗口落盘临时文件本来就归 JVM 临时目录（`compressTempFiles=true` 已在用），那是**瞬时 scratch**，与"对外保留的导出文件"是两回事，不冲突。
   - 结论：维持 `export.file-dir` 单点配置，本地默认 `backend/data/export`、容器指向命名卷；不做迁移。
2. **SXSSF 写入窗口以外的旧数据，会变成什么** → 不丢、也不留在内存：超过 `sxssf-row-window`（100）的行由 SXSSF **spool 到它自己的临时文件**（JVM 临时目录，`compressTempFiles=true` 已压缩其体积），内存只保留最近一个窗口；`workbook.write(output)` 时把"已 spool 的旧行 + 内存窗口内新行"**按序全部流式**写进输出流；`close()/dispose()` 后这些临时文件被释放。这正是"流式写防 OOM"的机理，与本期 `.tmp`→原子改名的改造无冲突（`write` 目标只是换成一个临时文件路径）。**不要在代码里手动"刷"窗口外数据——那是 SXSSF 的职责。**

```sql
-- finished_at：终态(SUCCESS/FAILED)回填，与 export_job_attempt.finished_at 同值，供导出中心【完成时间】列取值。
-- file_path/file_size：仅 SUCCESS 终态回填；FAILED/其它状态为 NULL。
ALTER TABLE export_jobs
    ADD COLUMN finished_at DATETIME DEFAULT NULL
        COMMENT '任务完成时间:终态(SUCCESS/FAILED)回填,与export_job_attempt.finished_at同值;导出中心【完成时间】列取此值'
        AFTER processed_rows,
    ADD COLUMN file_path VARCHAR(255) DEFAULT NULL
        COMMENT '成功导出文件相对路径(相对 export.file-dir, 形如 <jobId>/export.xlsx);仅SUCCESS后有值'
        AFTER finished_at,

        COMMENT '成功导出文件大小(字节);仅SUCCESS后有值'
        AFTER file_path;
```

要点：
- **不建索引**（finished_at/file_path/file_size 只随行读写，无查询谓词）；`updated_at` 由 `ON UPDATE CURRENT_TIMESTAMP` 自动刷新，无需手动 set。
- 存量库：历史行的 `finished_at` 为 NULL（9.0 的终态只在 attempt 上有 `finished_at`，job 级无从回填——**不回填历史**，本期只对之后落终态的任务写入）。
- 同步 `entity/ExportJob` 增 `finishedAt (LocalDateTime) / filePath (String) / fileSize (Long)` 三字段与 getter/setter（驼峰自动映射）；`ExportJobVO` record 追加 `LocalDateTime finishedAt`（放 `createdAt` 之后）并在 `ExportJobServiceImpl.toVO` 映射 `job.getFinishedAt()`。

## 四、后端改动 A：受控路径封装 `ExportFileStore`（root 归一化 + 越界校验 + 每任务目录）

新增 `export/support/ExportFileStore.java`（与 `OrderExportColumns` 同包，纯路径职责，不掺业务）：

```java
/**
 * 导出文件存储 —— 受控根目录(root=export.file-dir,配置管理)下的按任务隔离 + 越界守卫。
 *
 * <p>文件布局：root/<jobId>/export.xlsx.tmp →(原子改名)→ root/<jobId>/export.xlsx。
 * jobId 为 DB 自增 Long，天然安全；动态文件名绝不用用户输入(export_jobs.filename 仅供展示)。
 * 写盘/清理/(将来)下载一律经本类构造与解析路径；resolve() 供消费 DB 存回相对路径时做越界校验。
 */
public final class ExportFileStore {

    private final Path root;   // = Paths.get(fileDir).toAbsolutePath().normalize()

    public ExportFileStore(String rootDir) {
        this.root = Paths.get(rootDir).toAbsolutePath().normalize();
    }

    public Path taskDir(long jobId)        { return root.resolve(String.valueOf(jobId)); }
    public Path tmpFile(long jobId)        { return taskDir(jobId).resolve("export.xlsx.tmp"); }
    public Path finalFile(long jobId)      { return taskDir(jobId).resolve("export.xlsx"); }
    /** 入库/回写的相对路径(相对 root)：恒 "jobId/export.xlsx"。 */
    public String relativePath(long jobId) { return jobId + "/export.xlsx"; }

    /**
     * 把相对路径在受控 root 下解析并校验：越出 root 抛 IllegalArgumentException。
     * 写入/清理/(将来)下载统一走这里。核心就是 normalize 后 startsWith 判定。
     */
    public Path resolve(String relative) {
        Path p = root.resolve(relative).normalize();
        if (!p.startsWith(root)) {
            throw new IllegalArgumentException("导出文件路径越界, 拒绝: " + relative);
        }
        return p;
    }

    /** best-effort 删除某任务整个目录(失败清理/将来清扫用)；删不掉只记日志不抛。 */
    public void deleteTaskDir(long jobId) { /* 递归删除 taskDir(jobId)，IOException 吞掉记 warn */ }
}
```

实现要点：
- 构造时把 root 转绝对+归一化一次；所有路径统一经它产出。`resolve` 的判据就三行：`resolve → normalize → startsWith`——**不要加**符号链接到 `toRealPath` 追链、白名单字符集、格式审计等，本期威胁面只有"DB 存回相对路径被改"，startsWith 足矣（真有下载时，serving 前若担心软链，可再对已存在文件 `toRealPath()` 后二次 startsWith，写注释留档即可，本期不实现）。
- 在 `ExportJobServiceImpl` 构造函数由 `@Value("${export.file-dir:./data/export}")` 注入的同一字符串构造一个 `ExportFileStore` 字段，`executeExport` 全改用 `store.*`（见第六节），原 `fileDir` 字符串字段可删（被 store 取代）。
- 单测 `ExportFileStoreTest`（无 FS 也可测，用纯路径断言）：
  - `resolve("7/export.xlsx")` → `root/7/export.xlsx`；
  - `resolve("7/../6/export.xlsx")` → `root/6/export.xlsx`（normalize 归位，不越界则放行）——**注意**：`..` 只要没逃出 root 就合法，只有 `resolve("../x")`、`resolve("/etc/passwd")`、`resolve("a/../../x")` 这类越出 root 才抛；
  - 越界样例断言抛 `IllegalArgumentException`；
  - `relativePath(7).equals("7/export.xlsx")`、`tmpFile(7)/finalFile(7)` 同目录（`getParent()` 相等）。

> ponytail 注：本类就是"root 配置化 + 一处归一化守卫 + 每任务子目录"的最小载体，别扩展成虚拟文件服务/上传组件。将来下载接口一行 `store.resolve(job.getFilePath())` 即完成校验。

## 五、后端改动 B：金额文本化（`OrderExportColumns` + 单测）

`OrderExportColumns`：

1. `amount` 常量取值函数从 `(o.getAmount()==null ? ZERO : o.getAmount()).doubleValue()`（numeric）改为 `formatAmount(o.getAmount())`（返回 `String`）：
   ```java
   amount("订单金额", o -> formatAmount(o.getAmount())),
   ```
2. 新增包内可见纯函数（供测试直接调用）：
   ```java
   /** 金额 → 固定 2 位小数的纯文本("12"→"12.00","12.5"→"12.50",null→"0.00")；toPlainString 防科学计数 */
   static String formatAmount(BigDecimal amount) {
       BigDecimal v = amount == null ? BigDecimal.ZERO : amount;
       return v.setScale(2, RoundingMode.HALF_UP).toPlainString();
   }
   ```
   （`amount` 为 DECIMAL(12,2)，DB 值恒 ≤2 位小数，`setScale(2)` 本不会触发舍入；HALF_UP 只是防御异常数据。）
3. 枚举类注释与 `value(Order)` javadoc 同步更新："amount 走 STRING 单元格（固定 2 位小数的文本），不再 numeric"。**amount 不走 `sanitize`**（纯 BigDecimal 数值文本，STRING 单元格内负号/数字不会被当公式；走 sanitize 会给负值多加前导 `'`）。

`ExcelFileWriter.writeRow` 的 `Number` 分支：本期 amount 不再返回 Number，全列都落 String 分支。**保留现有 `Number` 分支不动即可**（防御将来加数值列），不必删。

单测（补进 `OrderExportColumnsTest`）：
- `formatAmount(new BigDecimal("12"))` → `"12.00"`（整数补位）；
- `formatAmount(new BigDecimal("12.5"))` → `"12.50"`；`formatAmount(null)` → `"0.00"`；
- 全链路：构造一个 `Order`（`setAmount(new BigDecimal("1200"))`），`OrderExportColumns.amount.value(order)` 返回 `"1200.00"`（`String`，非 `Number`）；`createdAt` 值仍是 `"yyyy-MM-dd HH:mm:ss"` 文本。

> ponytail 注：这是对 9.0"amount 走 numeric 可求和"的**有意反转**（需求方确认）。改完顺手在 `agent-reference/after/*phase9*` 文档补一行作废标注，避免 phase10 之后读到旧口径。

## 六、后端改动 C：`.tmp` 原子发布流转（executeExport + finalize 扩展）

这是本期核心时序改动。**改前先通读 `ExportJobService.claim / executeExport / finalizeJob` 与 `ExportJobConsumer` 现有实现与注释**，本文只改 execute 内文件产出段与 finalize 的字段集，**不动 claim / ack / 死信 / 重试结构**。

### 执行时序（executeExport 内部）

```text
executeExport(jobId):
  store = 注入的 ExportFileStore
  tmp   = store.tmpFile(jobId)        // root/<jobId>/export.xlsx.tmp
  out   = store.finalFile(jobId)      // root/<jobId>/export.xlsx  (与 tmp 同目录!)
  writer = new ExcelFileWriter(tmp, sxssfRowWindow)
  committed = 0
  try:
    job = selectById(jobId)                 // null → 抛(同现状)
    snapshot = readSnapshot(...)            // 解析失败→抛
    cols = readColumns(...)                 // 白名单外字段→抛(R3)
    writer.open()                           // 建 root/<jobId>/ 目录
    writer.writeHeader(...)
    committed = writeBatches(...)           // 同 9.0：keyset + 每批短事务 processed_rows+=size
    writer.close()                          // workbook flush → tmp 完整落盘(此刻 .xlsx 尚不存在)
    publishAtomically(tmp, out)             // ★ 原子发布：.tmp 被消费掉
    long size = Files.size(out)
    finalizeJob(jobId, SUCCESS, committed, null, store.relativePath(jobId), size)   // ★ 带 file 元信息
    log.info(...)
  catch (Throwable t):
    writer.disposeQuietly()
    deleteFileQuietly(tmp)                  // 半成品(未发布)或已发布都清
    deleteFileQuietly(out)                  // 已发布但未回写成功 → 也删, 不留孤儿(R7)
    store.deleteTaskDir(jobId)              // best-effort 清空目录(失败清理"不打扰")
    finalizeJob(jobId, FAILED, committed, reasonOf(t), null, null)   // FAILED 不带 file 字段
```

```java
/** 同目录同卷原子改名发布；ATOMIC_MOVE 不受支持时回退普通 move(同目录 rename 仍原子)。 */
private static void publishAtomically(Path tmp, Path out) throws IOException {
    try {
        Files.move(tmp, out, StandardCopyOption.ATOMIC_MOVE);
    } catch (AtomicMoveNotSupportedException e) {
        Files.move(tmp, out, StandardCopyOption.REPLACE_EXISTING);
    }
}
```

**三分支与摘要第 11~15 行严格对应**：
1. **原子发布成功 + 回写成功** → job/attempt=SUCCESS，`file_path=store.relativePath(jobId)`、`file_size=Files.size(out)` 已同事务落库；`.tmp` 已被 `move` 消费，**无残留、无需再删**。`taskDir` 内只留完整 `.xlsx`。
2. **发布前/发布中失败**（write/flush/move 抛错）→ catch 删 `.tmp`（半成品）→ `finalizeJob(FAILED)`（file 字段 null）；`.xlsx` 尚未产生，`deleteFileQuietly(out)` 是 no-op。
3. **发布成功但回写失败**（`finalizeJob(SUCCESS,...)` 抛，如 DB 不可用）→ 落入同 catch：删 `.tmp` **和已发布的 `.xlsx`** → 尝试 `finalizeJob(FAILED)`；若 FAILED 也落不下则抛出 → 消费者 `basicNack` → DLQ（job 可能留 RUNNING，即 9.0 已文档化的"卡死 RUNNING"边界，**不自动恢复**）。

### finalizeJob 扩展（file 元信息仅 SUCCESS 写）

现有 `finalizeJob(long, ExportJobStatus, long, String)` 扩一个重载/加参（Job attempt + job 两处 UPDATE 的 `TransactionTemplate` 结构原样保留）：

```java
finalizeJob(jobId, status, processed, errorMessage,
            String filePath /* 仅 SUCCESS 非空 */, Long fileSize /* 仅 SUCCESS 非空 */) {
  transactionTemplate.executeWithoutResult(tx -> {
      LocalDateTime now = LocalDateTime.now();     // 同一 now，job 与 attempt 的 finished_at 同值
      // attempt UPDATE：status、finished_at=now、error_message(仅 FAILED)
      // job UPDATE：status、processed_rows、finished_at=now；status==SUCCESS 时追加 set(file_path, filePath).set(file_size, fileSize)
      //             status==FAILED 时不 set file 两列（保持/为 NULL）
      // 两处影响行数=0 仍抛(同现状)
  });
}
```

- **成功**：`filePath = store.relativePath(jobId)`（相对路径入库），`fileSize = Files.size(out)`；`job.finished_at` 与 `attempt.finished_at` 均置 `now`。
- **失败**：`job.finished_at` 与 `attempt.finished_at` 均置 `now`（FAILED 也是"已完成"，导出中心要显示失败时间）；**不碰 file 两列**（新任务恒为 NULL；失败路径已把文件删净，无需清残留列）。
- **完成时间双写**：job 级 `finished_at` 是导出中心「完成时间」列的取值来源（前端绑 `job.finishedAt`），attempt 级 `finished_at` 保留 9.0 既有语义（本次执行结束时刻）；两者在 `finalizeJob` 里用**同一个 `now`**，保证不漂移。
- 不要把 `filePath` 当"对外展示名"用——`export_jobs.filename` 仍独立保存用户文件名（不进入路径，本阶段不对外命名）。

### ExcelFileWriter

除 `executeExport` 传入 `store.tmpFile(jobId)` 外，**writer 本身几乎不用改**：`open()` 里 `Files.createDirectories(parent)` 自动建出 `root/<jobId>/`；`close()` 写的就是 `.tmp`。仅把 `ExcelFileWriter` 的类注释/字段注释同步为"写盘对象是 `.tmp`，由调用方负责原子改名发布"。
